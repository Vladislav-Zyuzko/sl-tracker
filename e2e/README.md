# Сквозные тесты SL Tracker

Прогон против **живого API по HTTP**, а не против приложения, собранного внутри тестового
процесса. Здесь живёт то, чего не видно из модульных тестов и из e2e бэкенда: цепочки
состояний между запросами, два клиента одновременно, живой WebSocket, гонки на уровне HTTP
и соответствие опубликованному контракту `docs/api/openapi.json`.

Объём, границы и обоснование выбора инструментов — [docs/qa/test-plan.md](../docs/qa/test-plan.md).
Найденные дефекты — [docs/qa/defects.md](../docs/qa/defects.md).

## Запуск

```bash
cd e2e
npm install       # один раз
npm test          # весь набор
```

`run.mjs` делает всё сам: поднимает отдельный экземпляр API, ждёт `/api/health`, чистит
тестовую базу, гоняет `node --test` и гасит API — в том числе если прогон упал.
Весь набор — 265 проверок — проходит примерно за 35 секунд.

```bash
node run.mjs tests/realtime.test.mjs     # один файл
E2E_API_LOG=1 node run.mjs               # с логом API — нужно при разборе 500
E2E_TEST_NAME='D-26' node run.mjs        # только тесты, чьё имя совпало
E2E_TEST_TIMEOUT=30000 node run.mjs      # свой предел на тест (по умолчанию 120 с)
```

### Два флага раннера, которые важно не потерять

`--test-timeout` — зависший тест обязан упасть с указанием места. Тест, который висит
вечно, хуже упавшего: прогон не даёт ответа вообще.

`--test-force-exit` — без него набор из нескольких файлов встаёт **на три минуты после
каждого файла**, который много ходил по HTTP. Причина не в продукте: `fetch` держит
соединения в пуле keep-alive, из-за них процесс файла не завершается, а раннер ждёт
его завершения, прежде чем взять следующий файл. Закрыть этот пул из теста нечем —
Node не отдаёт наружу диспетчер своего `fetch`. Замер: `edge-cases.test.mjs` — 4 секунды
тестов и 193 секунды ожидания выхода; с флагом весь набор занимает 35 секунд.

### Что нужно заранее

1. Поднятое окружение: `infra/compose/docker-compose.dev.yml` (PostgreSQL, Redis, MinIO).
2. Собранный API: `cd apps/api && npm run build`. Раннер ждёт появления `dist/main.js`
   до 90 секунд — чужая сборка в этот момент прогон не ломает.
3. `.env` в корне репозитория: из него берутся доступы к базам и `SESSION_SECRET`.
4. Созданная и мигрированная база `sl_tracker_e2e` — один раз:

```bash
cd apps/api && POSTGRES_DB_OVERRIDE=sl_tracker_e2e npx drizzle-kit migrate
```

## Изоляция

Прогон не должен задевать ни рабочее окружение, ни тесты бэкенда:

| Ресурс | Рабочее | e2e бэкенда | Здесь |
|---|---|---|---|
| Порт API | 3000 | — | **3100** |
| PostgreSQL | `sl_tracker` | `sl_tracker_test` | **`sl_tracker_e2e`** |
| Redis | база 0 | база 15 | **база 14** |
| MinIO | `sl-attachments` | тот же | **`sl-tracker-e2e`** |

Своя база PostgreSQL нужна не только ради рабочих данных: e2e бэкенда делают `truncate`
всех таблиц, и общая с ними база означала бы, что чужой прогон сносит данные посреди
нашего сценария.

Сдвинуть можно переменными: `E2E_API_PORT`, `E2E_POSTGRES_DB`, `E2E_REDIS_DB`,
`E2E_MINIO_BUCKET`, `E2E_APP_BASE_URL`.

### Прогон против внешнего стенда

```bash
E2E_EXTERNAL_API=1 E2E_API_URL=https://tracker.example:8443 \
E2E_APP_BASE_URL=https://tracker.example:8443 node run.mjs
```

Свой API при этом не поднимается. Доступ к базе стенда всё равно нужен: без него харнесс
не выдаст сессию.

## Как тесты входят в трекер

Вход через Яндекс ID автоматизировать нельзя — он требует живого согласия человека.
Харнесс выпускает сессию сам, **не меняя продуктовый код**: пишет строку в `sessions`
тем же способом, что и `SessionService.create`, и предъявляет секрет `<sessionId>.<verifier>`
(см. `apps/api/src/sessions/session-token.ts`). `SessionService.resolve` не находит её
в Redis, поднимает из PostgreSQL и кэширует — дальше она ничем не отличается от выданной
настоящим входом, включая отзыв через `destroyAllForUser`.

Тестовый эндпоинт в API для этого не нужен и не предлагается: он добавил бы в боевой код
путь выдачи сессии без аутентификации.

## Устройство

```
run.mjs                  запуск: поднять API → почистить базу → node --test → погасить API
lib/config.mjs           чтение .env, адреса, изоляция ресурсов
lib/db.mjs               выдача сессий, создание пользователей, чтение того, что API не отдаёт
lib/redis.mjs            сброс счётчиков ограничения частоты
lib/api.mjs              HTTP-клиент: cookie sl_session + Origin, как у браузера
lib/ws.mjs               клиент живых обновлений по docs/api/websocket.md
lib/actors.mjs           действующие лица сценария и быстрая сборка сцены
tests/*.test.mjs         сами сценарии
```

Каждый актёр — своя сессия, как своя вкладка браузера. Для сценариев «два клиента
одновременно» это принципиально: общий клиент на всех спрятал бы ровно те ошибки,
ради которых сквозные тесты и пишутся.

## Правила, которых держится набор

- **Никаких `sleep`.** Ожидание строится на условии: `waitFor`, `waitForEvent`,
  `waitForClose`. Пауза вместо условия — это либо флак, либо замедление прогона.
- **Клиент не бросает исключение по коду ответа.** Ответ — данные; ожидание кода
  принадлежит тесту, иначе негативные сценарии пришлось бы писать через `try/catch`.
- **Сообщение об ошибке несёт настоящий ответ сервера.** Иначе падение теста приходится
  расследовать вручную.
- **Один тест — одна причина падения.** Если поведение уже закреплено отдельным тестом
  (например, расхождение кода ответа с контрактом — DEF-01), остальные тесты на него
  не падают: у них своя тема.
- **База — только для того, чего снаружи не сделать.** Сквозной тест, который лезет
  в базу вместо эндпоинта, проверяет не продукт, а собственное представление о нём.

## Красные тесты — это нормально

Набор красный, пока живы дефекты из [docs/qa/defects.md](../docs/qa/defects.md).
Тесты не приглушены (`skip`) и не подогнаны под фактическое поведение намеренно:
приглушённый тест — это дефект, о котором никто не вспомнит.

Ожидаемо красные прямо сейчас:

| Тест | Дефект |
|---|---|
| `contract-status-codes` → `POST /api/notifications/{id}/read`, `…/read-all` | DEF-01 |
| `concurrency` → `запись в удаляемую задачу отвечает 404, а не 500` | DEF-02 |
| `edge-cases` → `нулевой символ в тексте отклоняется…` | DEF-03 |
| `edge-cases` → `ошибка 400 несёт машиночитаемый код…` | DEF-04 |
| `filters-pagination` → `total сайдбара учитывает поиск…` | DEF-05 |

Всё остальное должно быть зелёным. Если позеленело что-то из таблицы — дефект исправлен,
и строку надо убрать отсюда и из реестра.
