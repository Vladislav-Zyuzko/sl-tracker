# Развёртывание SL Tracker

Ты работаешь **на боевом сервере**. Рядом крутятся чужие сервисы, которые ломать нельзя.
Читай раздел «Границы» до того, как выполнишь первую команду.

## Что это за проект

Веб-трекер задач: Flutter Web + NestJS + PostgreSQL 18 + Redis + MinIO, всё в Docker Compose
за обратным прокси Caddy. Репозиторий — `git@github.com:Vladislav-Zyuzko/sl-tracker.git`,
рабочая ветка `develop`, каталог на сервере `/opt/sl-tracker`.

Подробная человеческая инструкция лежит в самом репозитории: `infra/DEPLOY.md`.
**Прочитай её перед работой** — этот навык её не заменяет, а дополняет правилами для агента.

## Границы. Нарушать нельзя

1. **Никогда не выполняй `docker compose down -v`** и вообще ничего с флагом `-v` на боевых
   томах. Там база, вложения и сертификаты Let's Encrypt. Потеря сертификатов ещё и упирается
   в лимит выдачи — быстро восстановить не получится.
2. **Не трогай чужие контейнеры.** На сервере работают `amnezia-xray`, `amnezia-awg2`,
   `telegram-bot`, `claude-worker`. Они не наши. Останавливать, перезапускать, менять их
   настройки, освобождать их порты — запрещено.
3. **TCP 443 занят XRay и должен таким остаться.** Он маскирует VPN под HTTPS; отобрав порт,
   ты сломаешь пользователю обход блокировок. Трекер живёт на **8443**, это норма, а не сбой.
4. **Секреты не выводи.** Не печатай содержимое `.env`, не пересказывай пароли и ключи
   Яндекса, не вставляй их в отчёт. Проверять наличие можно длиной строки или `grep -c`.
5. **Не чини то, о чём не просили.** Увидел странность в чужом сервисе — скажи, не трогай.
6. **Перед любой необратимой операцией спроси человека.** К необратимым относятся: удаление
   томов, `git checkout` с потерей правок, перезапись `.env`, изменение конфигурации Docker
   или сети сервера.

## Проверь, что уже есть

Прежде чем что-то делать, определи состояние:

```bash
ls /opt/sl-tracker 2>/dev/null && echo "репозиторий на месте" || echo "первое развёртывание"
docker ps --format '{{.Names}}\t{{.Status}}' | grep -E 'sl-tracker|sl-' || echo "наши контейнеры не запущены"
```

Дальше выбери сценарий: **первое развёртывание** или **обновление версии**.

# Сценарий A. Первое развёртывание

## A1. Окружение

```bash
docker --version && docker compose version   # нужна v2, команда с пробелом
free -h                                       # памяти на сборку клиента нужно ~2 ГБ
sudo ss -tlnp | grep -E ':(80|8443) ' || echo "порты 80 и 8443 свободны"
```

**Стоп-условия:**
- нет Docker Compose v2 → скажи человеку, дальше не иди;
- порт 80 или 8443 занят → **не освобождай сам**, покажи, кто занял, и спроси;
- памяти меньше 2 ГБ и нет свопа → предложи добавить своп командами из `infra/DEPLOY.md`
  раздел 2, но выполняй только после согласия.

## A2. Код

Серверу нужен ключ только на чтение:

```bash
ls ~/.ssh/id_ed25519.pub 2>/dev/null || ssh-keygen -t ed25519 -C "sl-tracker deploy" -f ~/.ssh/id_ed25519 -N ""
cat ~/.ssh/id_ed25519.pub
```

Публичный ключ **покажи человеку** и попроси добавить в GitHub: репозиторий →
Settings → Deploy keys → Add deploy key, **без права записи**. Дождись подтверждения.

```bash
ssh -T git@github.com    # должно поздороваться
sudo mkdir -p /opt && sudo chown "$USER" /opt
git clone git@github.com:Vladislav-Zyuzko/sl-tracker.git /opt/sl-tracker
cd /opt/sl-tracker && git checkout develop
```

## A3. Файл `.env`

```bash
cd /opt/sl-tracker
[ -f .env ] && echo "ВНИМАНИЕ: .env уже есть, не перезаписывай" || cp .env.example .env
```

Сгенерируй пароли и **впиши их сам** в `.env` (человеку показывать не нужно):

```bash
for n in POSTGRES_PASSWORD REDIS_PASSWORD MINIO_ROOT_PASSWORD SESSION_SECRET; do
  echo "$n=$(openssl rand -base64 32 | tr -d '/+=')"
done
```

Адреса подставляются готовыми — сервер и имена уже проверены:

```ini
HTTP_PORT=80
HTTPS_PORT=8443
SL_DOMAIN=tracker.72-56-41-79.sslip.io
SL_S3_DOMAIN=s3.72-56-41-79.sslip.io
APP_BASE_URL=https://tracker.72-56-41-79.sslip.io:8443
MINIO_PUBLIC_URL=https://s3.72-56-41-79.sslip.io:8443
YANDEX_REDIRECT_URI=https://tracker.72-56-41-79.sslip.io:8443/api/auth/yandex/callback
```

**Что нужно спросить у человека** (в чат он это присылать не обязан — может вписать сам):

- `YANDEX_CLIENT_ID` и `YANDEX_CLIENT_SECRET` из кабинета oauth.yandex.ru;
- `SL_ACME_EMAIL` — почта для Let's Encrypt;
- `ACCESS_LIST_BOOTSTRAP_EMAILS` — адреса тех, кому можно входить, через запятую.
  **Это критично:** без них в трекер не войдёт никто, включая владельца. Адрес должен быть
  тем, который Яндекс возвращает в профиле.

Отдельно напомни человеку: в кабинете Яндекса нужно добавить Redirect URI
`https://tracker.72-56-41-79.sslip.io:8443/api/auth/yandex/callback` — **символ в символ,
вместе с портом**. Без этого вход не заработает.

Проверка без раскрытия значений:

```bash
grep -c 'change-me' .env          # должно быть 0
grep -c '^YANDEX_CLIENT_ID=.\+' .env   # должно быть 1
grep -c '^ACCESS_LIST_BOOTSTRAP_EMAILS=.\+@' .env  # должно быть 1
git check-ignore -v .env          # должен показать правило игнорирования
chmod 600 .env
```

## A4. Сборка и запуск

```bash
cd /opt/sl-tracker
docker compose -f infra/compose/docker-compose.prod.yml --env-file .env build
```

Сборка клиента идёт 5–15 минут: внутри образа скачивается Flutter SDK. Это нормально.
Если процесс убит с сообщением `Killed` — не хватило памяти, вернись к свопу.

```bash
docker compose -f infra/compose/docker-compose.prod.yml --env-file .env up -d
docker compose -f infra/compose/docker-compose.prod.yml --env-file .env ps
```

Порядок соблюдается сам: данные ждут состояния healthy, затем одноразовый контейнер
применяет миграции, и только при его успешном завершении стартуют API и прокси.

```bash
docker compose -f infra/compose/docker-compose.prod.yml --env-file .env logs api-migrate
```

В логе должно быть видно поимённо, какие миграции применились.

## A5. Проверка

```bash
curl -sS https://tracker.72-56-41-79.sslip.io:8443/api/health
```

Ожидается `{"status":"ok","postgres":{"status":"up"...`.

Затем **попроси человека открыть** `https://tracker.72-56-41-79.sslip.io:8443` и войти
через Яндекс ID. Сам ты этого сделать не сможешь: нужен интерактивный вход в аккаунт.

## A6. Резервные копии

```bash
cd /opt/sl-tracker && ./infra/scripts/backup-db.sh
crontab -l 2>/dev/null | grep -q backup-db || (crontab -l 2>/dev/null; echo "0 4 * * * cd /opt/sl-tracker && ./infra/scripts/backup-db.sh >> backups/backup.log 2>&1") | crontab -
crontab -l | grep backup-db
```

Скажи человеку: копия лежит на том же сервере и от его потери не спасает — раз в неделю
архив стоит забирать к себе.

# Сценарий B. Обновление версии

```bash
cd /opt/sl-tracker && ./infra/scripts/deploy.sh
```

Скрипт забирает код из `develop`, собирает образы, ждёт готовности данных, применяет
миграции, перезапускает приложение и проверяет, что оно ожило. При ошибке останавливается —
это задумано, приложение не должно поехать на сломанной базе.

Если скрипт упал, **не обходи его руками**: разбери причину по выводу и логам.

# Разбор частых отказов

| Симптом | Причина и что делать |
|---|---|
| Caddy не получил сертификат | Чаще всего закрыт 80-й порт на файрволе **хостинга**, а не в `ufw`. Проверь `docker compose ... logs caddy`. Скажи человеку проверить панель провайдера. Второе по частоте — исчерпан лимит Let's Encrypt после серии неудач: тогда надо ждать, а не повторять. |
| Сборка клиента `Killed` | Не хватило памяти. Своп из `infra/DEPLOY.md` раздел 2. |
| `api-migrate` завершился с ненулевым кодом | Миграция упала. Смотри её лог. **Не запускай API вручную в обход** — на полумигрированной базе он наломает данных. |
| Вход отвечает `unauthorized_client` | Приложение в Яндексе не прошло модерацию или изменились права. Это на стороне человека. |
| Вход отвечает отказом доступа | Адреса нет в `ACCESS_LIST_BOOTSTRAP_EMAILS`, либо он не совпадает с тем, что вернул Яндекс. Проверка идёт до создания сессии — это защита, а не сбой. |
| `provider_unavailable` при входе | Сервер не смог поговорить с Яндексом. Проверь сеть с сервера: `curl -s -o /dev/null -w '%{http_code}' https://login.yandex.ru/info`. |
| Порт 8443 недоступен снаружи | Файрвол хостинга. Изнутри проверь `curl -k https://localhost:8443/api/health`. |

# Полезные команды

```bash
# Логи (последние 100 строк)
docker compose -f infra/compose/docker-compose.prod.yml --env-file .env logs --tail=100 api

# Состояние
docker compose -f infra/compose/docker-compose.prod.yml --env-file .env ps

# Остановка без потери данных
docker compose -f infra/compose/docker-compose.prod.yml --env-file .env down

# Откат на предыдущую версию кода
git log --oneline -10
./infra/scripts/deploy.sh <хеш>
```

# Как отчитываться

Человек не видит твой вывод целиком. В конце работы скажи коротко:

- что сделано и на какой версии сейчас стоит стенд (`git rev-parse --short HEAD`);
- какие проверки прошли, с фактическим результатом, а не «всё хорошо»;
- что **не** проверено (например, вход через Яндекс ID ты проверить не можешь);
- что осталось сделать человеку.

Если шаг не выполнен — скажи прямо, что он не выполнен, и почему. Не выдавай пропущенную
проверку за пройденную: на боевом сервере это дороже, чем где бы то ни было.
