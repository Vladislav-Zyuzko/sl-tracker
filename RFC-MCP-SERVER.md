# RFC: машинный доступ к SL Tracker для MCP-сервера

- **Статус:** предложение (нужно решение владельца)
- **Дата:** 2026-09-24
- **Автор:** внешний оркестратор (сессия ai-challenge, задача MCP)
- **Адресат:** Claude-харнесс репозитория `sl-tracker` (оркестратор + сабагенты `sl-backend-engineer`, `sl-qa`, `sl-frontend-engineer`)
- **Основание:** пользователь решил — делаем **PAT-эндпоинты**, машинная идентичность — **бот-пользователь**; правки в этом репозитории делает здешний харнесс.

---

## 1. Зачем

Рядом с трекером ставится **`sl-tracker-mcp`** — отдельный MCP-сервер, который даёт агентам
(dsh-term, Claude Code, любой MCP-клиент) пять операций над задачами:

| Инструмент MCP | Что делает | Эндпоинт SL Tracker |
|---|---|---|
| `create_task` | создать задачу с заголовком и описанием | `POST /api/queues/{key}/issues` |
| `update_task_description` | изменить описание | `PATCH /api/issues/{key}` |
| `add_comment` | добавить комментарий | `POST /api/issues/{key}/comments` |
| `get_task` | прочитать задачу | `GET /api/issues/{key}` |
| `set_task_status` | сменить статус | `PATCH /api/issues/{key}` |

**Функциональности API уже хватает** — все пять операций и справочники (`/api/projects`,
`/api/projects/{slug}/queues`, `/api/queues/{key}/statuses`) существуют и покрыты OpenAPI.
Не хватает только одного: **способа предъявить API машинный доступ**. Сегодня сессию
создаёт лишь OAuth-колбэк Яндекса, то есть неинтерактивный клиент войти не может.

Этот RFC описывает минимальные аддитивные изменения в SL Tracker, которые закрывают ровно
эту дыру, и не меняет ничего в существующих сценариях веб-клиента.

## 2. Что уже есть (и почему мы это переиспользуем)

| Механизм | Факт из кода | Следствие для решения |
|---|---|---|
| Две стратегии сессии | `SessionGuard`/`extractToken`: cookie `sl_session` **или** `Authorization: Bearer <id>.<verifier>` (ADR-0002) | bearer уже работает: `PAT` не требует нового способа аутентификации |
| Формат токена | `<sessionId>.<верификатор 32 байта>`, в БД только HMAC-SHA256 с `SESSION_SECRET` (`session-token.ts`) | PAT хешируется тем же механизмом, дамп БД не даёт предъявить токен |
| TTL и продление | `SESSION_TTL_SECONDS = 30 дней`, `touch()` продлевает при использовании | для PAT нужен **явный** срок (см. §5.3) |
| Отзыв доступа | `AccessListService.remove` → `sessions.destroyAllForUser(userId)` | отзыв доступа **немедленно гасит и PAT** бота — готовый kill-switch |
| Кэш | Redis: `sl:session:<id>`, `sl:sessions:by-user:<userId>` | PAT автоматически получает быстрый путь проверки и корректный отзыв |
| Список доступа | `access_entries` (email, `source`: config/manual/invitation, `isInstanceOwner`) | бота надо завести и в `users`, и в `access_entries` — тогда он «внутри периметра» и управляем |
| Членство в проекте | `project_members` (role: admin/member/reader); добавление — **только через приглашение** | приглашение требует входа, бот войти не может → нужен bootstrap-путь (§5.2) |
| Идентичности | `identities` (provider/external_id) нужны только для **входа** | бот без `identities` корректен: он никогда не логинится |
| Bootstrap из env | `AccessBootstrapService`: `ACCESS_LIST_BOOTSTRAP_EMAILS` применяется идемпотентно на старте | тот же приём для бота |

## 3. Решение (обзор)

1. **PAT = долгоживущая bearer-сессия с назначением `pat`.** Не новая сущность
   аутентификации, а расширение уже существующей: добавляем в `sessions` три аддитивных
   поля (`label`, `purpose`, `token_prefix`). Так PAT бесплатно получает хеширование,
   Redis-кэш, скользящий `lastSeenAt` и отзыв вместе с доступом.
2. **API управления токенами** (self-service, owner-aware):
   `POST /api/tokens`, `GET /api/tokens`, `DELETE /api/tokens/{id}`.
3. **Бот-пользователь из env** (`MCP_BOT_EMAIL` и родственные переменные) — идемпотентный
   bootstrap на старте API: `users` + `access_entries` (`source=config`) + `project_members`
   для перечисленных проектов. Создаётся один раз, дальше источник правды — БД.
4. **Маршрут для MCP** в Caddy (`{$SL_MCP_DOMAIN}` → контейнер `mcp:8080`), плюс сам
   контейнер — отдельный compose-проект на сети `sl-tracker_default`.
5. **MCP-сервер** (`sl-tracker-mcp`) ходит в API по внутренней сети
   (`http://api:3000`) с токеном бота. Он не знает про dsh, зависит только от HTTP API.

Детали реализации — в двух спецификациях:

- [`SPEC-PAT-API.md`](SPEC-PAT-API.md) — схема БД, миграция, эндпоинты, DTO, правила
  доступа, bootstrap бота, тесты, экран в вебе.
- [`SPEC-MCP-DEPLOY.md`](SPEC-MCP-DEPLOY.md) — что добавить в `infra/` (Caddy, compose, env)
  и как это проверяется.

## 4. Границы (что сознательно НЕ делаем)

- **Не** реализуем OAuth-авторизацию для MCP-сервера: PAT в заголовке достаточно для
  личного трекера; OAuth (RFC 9728 / protected resource metadata) — возможное развитие,
  но не в этой итерации.
- **Не** добавляем MCP-ресурсы и промпты: только инструменты (`tools`).
- **Не** трогаем существующие маршруты и их поведение: все изменения аддитивные.
- **Не** выдаём PAT по логину/паролю и не заводим локальный логин.
- **Не** даём PAT управлять токенами (см. §5.4) — иначе утечка токена размножается.
- **Не** добавляем «добавить участника в проект» отдельным маршрутом: членство бота
  приходит из env (при желании — отдельной задачей позже, вместе с экраном).
- **Не** храним PAT в открытом виде нигде: ни в БД, ни в Redis, ни в логах.

## 5. Ключевые проектные решения

### 5.1 PAT — это сессия, а не новая таблица

Альтернатива — отдельная таблица `api_tokens` со своим путём проверки в guard. Отвергнута:
это второй механизм аутентификации в горячем пути запроса, дублирование кэша, хеширования
и семантики отзыва. Расширение `sessions` даёт всё то же одной миграцией и без изменений
в `SessionGuard`.

### 5.2 Бот создаётся bootstrap-ом, а не приглашением

Приглашение предполагает принятие залогиненным человеком; у бота нет `identities`, и
входить ему незачем. Поэтому бот заводится тем же способом, что и первая запись доступа:
идемпотентно из env на старте API. Состав проектов тоже из env — в MVP этого достаточно,
а управление ботом из UI остаётся возможным развитием.

### 5.3 У PAT явный срок, у сессии — скользящий

Сессия живёт 30 дней и продлевается при использовании — для браузера это правильно.
Для токена, который лежит в env контейнера, «тихое» продление означало бы бессрочный
доступ. Поэтому у PAT срок задаётся при создании (`expiresInDays`, по умолчанию 365,
`null` — бессрочно с явным предупреждением), и он **не продлевается** автоматически;
`lastSeenAt` продолжает обновляться для аудита.

### 5.4 PAT не управляет токенами

`POST /api/tokens` и `DELETE /api/tokens/{id}` требуют **браузерной (cookie) сессии**
владельца. Запрос с PAT получает `403 pat_cannot_manage_tokens`. Так утечка токена не
даёт выпустить новые или отозвать чужие; управление остаётся в руках человека.

### 5.5 Права бота — права пользователя

MCP действует **от имени бота** и подчиняется тем же правилам: список доступа, членство
и роль в проекте (`member`), проверки на «автор/исполнитель — участник проекта». Никаких
обходов ACL: если бота убрать из проекта или отозвать доступ, MCP немедленно теряет
возможности — и заодно все его токены.

## 6. Требования к результату (acceptance criteria)

Проверяются на живом инстансе (`https://tracker.72-56-41-79.sslip.io:8443`).

1. **Бот существует.** В `users` есть запись с email из `MCP_BOT_EMAIL`; в `access_entries`
   — запись с `source=config`, `isInstanceOwner=false`, привязанная к этому `userId`; бот
   состоит в перечисленных в `MCP_BOT_PROJECTS` проектах с ролью из `MCP_BOT_PROJECT_ROLE`.
2. **Токен выпускается.** `POST /api/tokens` из-под cookie владельца с
   `{"name":"dsh-mcp","userId":"<bot>"}` возвращает токен **один раз**, а в списке
   `GET /api/tokens` видны имя, префикс, срок и `lastSeenAt`, но не секрет.
3. **Токен работает.**
   `curl -H "Authorization: Bearer <token>" .../api/me` → 200 с данными бота;
   `POST /api/queues/SL/issues` с этим токеном создаёт задачу от имени бота.
4. **Отзыв немедленный.** `DELETE /api/tokens/{id}` → следующий запрос с этим токеном
   даёт 401 `session_expired`. Отзыв доступа бота (`DELETE /api/access-entries/{id}`)
   гасит **все** его токены и завершает его сессии.
5. **PAT не управляет токенами.** `POST /api/tokens` с PAT → 403 `pat_cannot_manage_tokens`.
6. **Веб-клиент не сломан.** Вход по Яндексу, cookie-сессии, инвайты, отзыв доступа —
   без изменений; существующие тесты API зелёные; миграция применяется на пустой БД и на
   БД с данными (аддитивные колонки с дефолтами).
7. **Секрет не течёт.** Токен отсутствует в БД (только HMAC), в Redis (только hash),
   в логах и в ответах `GET /api/tokens`.

## 7. План внедрения (для здешнего харнесса)

| Шаг | Кто | Результат |
|---|---|---|
| 1 | `sl-backend-engineer` | Миграция + схема + `SessionService` (label/purpose/prefix, срок, список, отзыв) |
| 2 | `sl-backend-engineer` | `tokens` модуль: контроллер, DTO, правила доступа, rate limit, Swagger |
| 3 | `sl-backend-engineer` | Bootstrap бота из env + переменные в `config` и `.env.example` |
| 4 | `sl-qa` | Юнит/integration/e2e по §6; проверка, что PAT не управляет токенами и что отзыв гасит всё |
| 5 | `sl-frontend-engineer` + `sl-designer` | Экран «Токены доступа» в профиле (список/создание/показ один раз/отзыв) |
| 6 | оркестратор | `infra/`: site-блок Caddy + переменные (`SPEC-MCP-DEPLOY.md`), обновление `docs/api`, ADR |
| 7 | оркестратор | Деплой на сервер и проверка AC на живом инстансе |

Оценка: шаги 1–4 — примерно один рабочий цикл backend-агента с ревью; шаг 5 — отдельный
цикл фронта; шаги 6–7 — короткие.

## 8. Риски

| Риск | Как снижаем |
|---|---|
| Токен утечёт из env контейнера | короткий (365 дней) срок по умолчанию, `GET /api/tokens` показывает `lastSeenAt`, отзыв одной командой, PAT не размножается |
| Бот получит лишние права | роль `member`, только перечисленные проекты, никакого `isInstanceOwner`; при желании — ACL-экран остаётся источником правды |
| Миграция заденет прод | только `ADD COLUMN ... DEFAULT ...` и новый enum-тип; проверка на копии БД; `down`-сценарий — откат кода при совместимой схеме |
| Падение API при bootstrap бота | bootstrap идемпотентен и не блокирует старт при некорректном env (пишет warning, как `ACCESS_LIST_BOOTSTRAP_EMAILS`) |
| MCP-сервер станет «дыркой» в трекер | отдельный домен, обязательный bearer для MCP-клиентов, Origin-проверка, режим readonly, allowlist очередей — см. `SPEC-MCP-DEPLOY.md` |

## 9. Что нужно решить владельцу

2. **Проект(ы) бота**: в какие проекты его включить (ключи/слаги), роль — `member`?
3. **Имя и email бота**: предлагаю `SL Bot` и `sl-bot@sl-tracker.local` (внутренний адрес,
   по нему бот и попадает в список доступа).
4. **Экран токенов в UI**: делаем в этой итерации или после того, как MCP заработает
   (тогда первый токен выпускается запросом из-под cookie владельца)?
