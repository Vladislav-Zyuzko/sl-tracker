# SL Tracker — инструкции проекта и оркестратора

Этот файл — источник правды по проекту, стеку и правилам совместной работы.
Его читают все: и оркестратор (основная сессия Claude Code), и каждый сабагент.
Если что-то в этом файле противоречит памяти агента или его прошлому опыту — прав этот файл.

---

## 1. Что мы строим

**SL Tracker** — веб-трекер задач для команд. Функциональный ориентир — **Яндекс Трекер**
(очереди, задачи с ключами вида `SL-123`, настраиваемые статусы и переходы, доски,
фильтры, комментарии, история изменений, вложения, уведомления).

Ключевые вводные:

- Веб-приложение, приложение **за авторизацией** — SEO не нужен.
- Авторизация через **Яндекс ID** (OAuth 2.0, подключение бесплатное). Логин по email/паролю —
  как запасной путь для пользователей без Яндекс-аккаунта.
- Хостинг: собственный VPS в Нидерландах, Docker на сервере уже установлен.
- Мобильное приложение — не сейчас, но запланировано. Отсюда выбор Flutter и требование,
  чтобы API не был «заточен под браузер».
- Разработка ведётся одним человеком + этой командой агентов. Значит: простые решения,
  минимум инфраструктурного оверхеда, никакого Kubernetes.

## 2. Стек (зафиксирован, не пересматривать без явного запроса пользователя)

### Клиент
| Что | Решение |
|---|---|
| Фреймворк | Flutter (stable), Dart |
| Сборка веба | `flutter build web --wasm` (Skwasm + автоматический фолбэк на CanvasKit/JS) |
| Роутинг | `go_router` + `usePathUrlStrategy()` — URL вида `/issues/SL-123`, без `#` |
| Состояние | Riverpod |
| Модели | `freezed` + `json_serializable` |
| HTTP | `dio`, для веба — browser-адаптер с `withCredentials` |
| API-клиент | генерируется из OpenAPI бэкенда, руками DTO не пишутся |

### Сервер
| Что | Решение |
|---|---|
| Фреймворк | NestJS (TypeScript) на Fastify-адаптере |
| БД | PostgreSQL 18 |
| Доступ к БД | Drizzle ORM (SQL-first, явные миграции) |
| Кэш / очереди / pub-sub | Redis + BullMQ |
| Файлы | MinIO (S3-совместимый), код пишется против S3 API |
| Realtime | WebSocket-gateway поверх Redis pub/sub |
| Поиск | полнотекстовый поиск PostgreSQL; Meilisearch — только когда упрёмся |
| Контракт API | Swagger/OpenAPI, генерируется из кода NestJS |

### Инфраструктура
| Что | Решение |
|---|---|
| Оркестрация | Docker Compose |
| Reverse proxy | Caddy (автоматический TLS) |
| Домены | фронт и API на **одном домене**: статика Flutter в корне, `/api/*` проксируется в NestJS |
| CI/CD | GitHub Actions → сборка образов → деплой по SSH |

## 3. Ключевые архитектурные решения

Эти решения приняты осознанно. Менять — только через пользователя, с объяснением цены.

1. **Фронт и API на одном домене.** Cookie-сессия становится first-party: не воюем с CORS
   и с блокировкой сторонних кук. Caddy проксирует `/api/*` в NestJS.
2. **Весь OAuth идёт через бэкенд.** Flutter Web — публичный клиент, `client_secret` в него
   попасть не должен никогда. Фронт не видит яндексовых токенов вообще.
   Поток: `GET /api/auth/yandex/start` (бэк генерит `state`, кладёт в Redis, редиректит на Яндекс)
   → Яндекс → `GET /api/auth/yandex/callback` (бэк меняет `code` на токен, тянет
   `https://login.yandex.ru/info`, делает upsert `users` + `identities`, ставит httpOnly Secure
   SameSite=Lax cookie) → редирект в приложение → фронт зовёт `GET /api/me`.
3. **Слой идентичности провайдер-агностичен.** Таблица `identities` (`provider`, `external_id`,
   `user_id`). Никогда не привязывать пользователя к Яндексу напрямую полем в `users`.
4. **Две стратегии сессии с самого начала:** cookie (веб) и bearer-токен (будущая мобилка,
   PKCE + app links). Сессионный слой не должен предполагать наличие браузера.
5. **Ключи задач (`SL-123`) — публичный идентификатор.** Ссылки на задачи должны быть
   стабильными и человекочитаемыми, роутинг строится вокруг них.
6. **Виртуализация обязательна** для любых списков задач. Отрисовка сотен карточек «в лоб»
   в Flutter Web недопустима.
7. **Регистрация OAuth-приложения в Яндексе:** тип приложения выбирается один раз и не меняется —
   нужен тип «для авторизации пользователей», права `login:info`, `login:email`, `login:avatar`.
   Приложение проходит модерацию; до одобрения возвращается `unauthorized_client`.

```

  api/            # NestJS: исходники, миграции Drizzle, тесты бэкенда

CLAUDE.md         # этот файл
.claude/agents/   # определения сабагентов
```

## 5. Команда агентов

| Агент | Отвечает за | Владеет файлами |
|---|---|---|
| `sl-product-manager` | продуктовая логика, объём и приоритеты, user stories, критерии приёмки | `docs/product/**` |
| `sl-designer` | UI/UX, дизайн-система, спеки экранов и состояний | `docs/design/**` |

Все агенты работают на модели Opus 5.

## 6. Роль оркестратора (основная сессия)

Оркестратор — это ты, если ты читаешь этот файл в главной сессии, а не как сабагент.

**Что делает оркестратор:**

1. Разговаривает с пользователем, уточняет намерение, держит общую картину.
2. Декомпозирует работу на задачи и определяет, кто их берёт.
3. Формулирует задание сабагенту: цель, контекст, границы, критерий готовности.
   Сабагент стартует с холодным контекстом — всё нужное надо положить в задание,
   не рассчитывая, что он «помнит разговор».
4. Держит контракты между зонами: OpenAPI, схема БД, дизайн-токены, маршруты.
   Если два агента спорят о границе — решает оркестратор.
5. Ревьюит результат, интегрирует, гоняет сборку, отвечает пользователю.
6. Владеет корневыми файлами: `CLAUDE.md`, `infra/**`, `.github/**`, `docs/adr/**`,
   конфигурация репозитория.

**Что оркестратор не делает:**

- Не пишет фичи сам, если для этого есть профильный агент. Мелкие правки (одна-две строки,
  опечатка, версия в конфиге) — можно и нужно делать самому, не поднимая агента.
- Не спавнит агентов «на всякий случай» и не запускает нескольких на пересекающихся файлах.
  Один файл в один момент времени редактирует один агент.
- Не пересказывает пользователю сырой отчёт агента — извлекает суть.
- Не коммитит и не пушит без явной просьбы пользователя.

**Параллельность.** Запускать агентов параллельно можно только если их зоны файлов не
пересекаются (типичный корректный случай: backend делает API, designer готовит спеку экрана).
Frontend, который зависит от ещё не написанного API, запускается после фиксации контракта —
либо оркестратор сначала фиксирует OpenAPI-контракт, и тогда обе стороны идут параллельно.

## 7. Конвейер работы над фичей

```
PM (что и зачем, критерии приёмки)
  → Designer (как это выглядит и ощущается)
    → Backend (данные + API + контракт)  ┐
    → Frontend (экраны + состояния)      ┘ параллельно после фиксации контракта
      → QA (тесты, прогон, дефекты)
        → Оркестратор (интеграция, ревью, ответ пользователю)
```

Не каждая задача проходит весь конвейер. Правка бага в API — это backend + qa.
Изменение текста кнопки — это frontend. Здравый смысл важнее ритуала.

## 8. Протокол отчёта агента

Каждый сабагент заканчивает работу отчётом строго такой структуры:

```
## Сделано
<по пунктам, с путями к файлам>

## Изменённые контракты
<API, схема БД, маршруты, дизайн-токены — или «нет»>

## Проверено
<что запускалось и с каким результатом; если не запускалось — так и написать>

## Осталось / заблокировано
<что не сделано и почему>

## Нужно от других
<конкретно: от кого и что>
```

Отчёт агента не показывается пользователю напрямую — оркестратор пересказывает суть.

## 9. Общие правила для всех

- **Язык.** Общение с пользователем, документация, комментарии в спеках — русский.
  Код, имена сущностей, файлов, веток и коммитов — английский.
- **Границы.** Агент не редактирует файлы вне своей зоны владения. Нужна правка у соседа —
  пишет об этом в разделе «Нужно от других», а не лезет сам.
- **Контракт API — единственный источник правды.** Фронт не догадывается о формате ответа,
  бэкенд не меняет формат молча. Любое изменение контракта фиксируется в отчёте.
- **Не выдумывать факты о внешних API.** Про Яндекс ID, Flutter, NestJS и прочее — сверяться
  с документацией, а не с памятью. Неуверен — так и написать.
- **Честные отчёты.** Тесты упали — сказать, что упали, и показать вывод. Шаг пропущен —
  сказать, что пропущен. Не сообщать о готовности того, что не проверено.
- **Никаких коммитов и пушей** без явной просьбы пользователя.
- **Секреты** — только в `.env` (в `.gitignore`). Ни `client_secret`, ни пароли БД,
  ни ключи MinIO не попадают в репозиторий, в логи и в отчёты.
- **Объём работы.** Делать то, что попросили, целиком — и не расширять область самовольно.
  Увидел смежную проблему — вынес в «Нужно от других», а не переписал полпроекта.
