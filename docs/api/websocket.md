# SL Tracker — протокол живых обновлений (WebSocket)

Этот документ — **контракт** между сервером и клиентом по живым обновлениям.
OpenAPI WebSocket не описывает, поэтому `openapi.json` здесь не поможет: всё, что
нужно для написания клиента, находится тут.

Требование продукта — D-26: изменения задачи, новые комментарии и счётчик
непрочитанных появляются у другого пользователя **не позднее чем через 5 секунд**
и без перезагрузки страницы. Списки задач под это требование не попадают.

Реализация: `apps/api/src/realtime/`.

---

## 1. Главное в двух абзацах

Событие — это **сигнал**, а не состояние. Оно говорит «в этой теме случилось вот
что» и несёт минимум полей для навигации. Полные данные клиент забирает обычным
HTTP-запросом — тем же самым, которым он их уже загружает. Поля внутри события
названы так же, как одноимённые поля в ответах REST (`key`, `id`, `type`,
`role`, `userId`, `unreadCount`), чтобы у одного и того же не было двух форм.

Доставка **не гарантирована**. Redis pub/sub ничего не хранит, сокет может быть
закрыт, сеть — пропасть. Живое обновление ускоряет интерфейс, но не является
источником правды: пропущенное событие клиент восполняет при следующем действии
пользователя или при переподключении. Клиент, который без WebSocket ломается, —
написан неправильно.

---

## 2. Адрес и рукопожатие

```
wss://<домен>/api/ws
```

Тот же домен и тот же префикс `/api`, что и у HTTP (ADR-0001), — Caddy проксирует
`/api/*` целиком, включая `Upgrade`.

### Аутентификация

Ровно те же две стратегии, что и у HTTP (ADR-0002), и та же серверная проверка
сессии:

| Клиент | Как предъявляется сессия | Дополнительно |
|---|---|---|
| Веб | cookie `sl_session` (httpOnly, отправляется браузером сама) | заголовок `Origin` **обязан** совпадать с адресом приложения |
| Мобильный | заголовок `Authorization: Bearer <токен>` | — |

Заголовки для WebSocket из браузерного JS задать нельзя — веб-клиент ничего
специально не делает, cookie уходит сама. Мобильный клиент ставит `Authorization`
на рукопожатие.

Если сессии нет, она погашена или `Origin` не совпал, **соединение не открывается
вовсе**: сервер отвечает `401 Unauthorized` на рукопожатие. Открытого и тут же
закрытого сокета не бывает — это ошибка на этапе HTTP, и обрабатывать её надо как
«надо перелогиниться».

### Что приходит сразу после открытия

```json
{ "type": "ready", "topics": ["user:me"], "heartbeatSeconds": 30, "maxTopics": 20 }
```

Сервер сам подписывает соединение на тему `user:me` — счётчик непрочитанных нужен
на каждом экране, и просить его отдельной командой незачем. Всё остальное клиент
запрашивает сам.

---

## 3. Формат сообщений

Все кадры — текстовые, JSON-объекты. Бинарные кадры сервер не отправляет и не ждёт.

### Клиент → сервер

| Команда | Кадр |
|---|---|
| Подписаться | `{"type":"subscribe","id":"<корреляция>","topic":"issue:DEV-42"}` |
| Отписаться | `{"type":"unsubscribe","id":"<корреляция>","topic":"issue:DEV-42"}` |
| Проверить связь | `{"type":"ping","id":"<корреляция>"}` |

`id` — произвольная строка (до 64 символов), которую сервер вернёт в ответе.
Сопоставлять ответ с запросом надо по ней, а не по порядку кадров. Поле
необязательное; без него в ответе будет `"id": null`.

### Сервер → клиент

| Кадр | Когда |
|---|---|
| `{"type":"ready","topics":[…],"heartbeatSeconds":30,"maxTopics":20}` | сразу после открытия |
| `{"type":"subscribed","id":"1","topic":"issue:DEV-42"}` | подписка принята |
| `{"type":"unsubscribed","id":"2","topic":"issue:DEV-42"}` | подписка снята |
| `{"type":"pong","id":"3"}` | ответ на `ping` |
| `{"type":"error","id":"1","code":"…","message":"…"}` | команда отклонена |
| `{"type":"event","topic":"…","event":"…","at":"…","actorId":"…","data":{…}}` | произошло событие |

### Коды ошибок

| `code` | Что значит |
|---|---|
| `invalid_message` | кадр не JSON-объект |
| `unknown_command` | неизвестное значение `type` |
| `invalid_topic` | тема не указана, слишком длинная или не разбирается (в том числе `user:<чужой-id>`) |
| `topic_forbidden` | темы нет **или** она недоступна — снаружи эти случаи неотличимы |
| `too_many_topics` | превышен предел тем на одно соединение (`maxTopics`) |

Ошибка команды **не закрывает** соединение: клиент может продолжать работать.

## 4. Темы

| Ярлык при подписке | Что приносит | Кто имеет право |
|---|---|---|
| `issue:DEV-42` | комментарии, изменения полей, записи истории, вложения, удаление задачи | любой участник проекта задачи, включая читателя |
| `project:my-team` | состав участников проекта | любой участник проекта |
| `user:me` | свои уведомления и счётчик непрочитанных | только сам пользователь; подписан автоматически |

Правила:

- **Ключ задачи регистронезависим** (ADR-0004): `issue:dev-42` и `issue:DEV-42` —
  одна тема.
- **Короткое имя проекта может быть прежним** (US-18): подписка по старому имени
  работает.
- **Канонический ярлык возвращает сервер.** В `subscribed` и во всех событиях
  приходит канонический вид (`issue:DEV-42`, `project:<текущее-имя>`, `user:me`).
  Сравнивать темы событий надо с ним, а не с тем, что было отправлено.
- Чужая тема пользователя (`user:<uuid>`) не принимается вовсе — это
  `invalid_topic`, а не отказ в праве.
- Отписка идемпотентна: незнакомая тема тоже отвечает `unsubscribed`.

### Права проверяются дважды

При подписке — теми же сервисами, что обслуживают соответствующий HTTP-запрос.
И **при каждой рассылке** — заново. Сокет живёт часами, а человека могли исключить
из проекта уже после подписки. Исключённый получает по этой теме

```json
{ "type": "error", "id": null, "code": "topic_forbidden", "message": "Тема недоступна" }
```

и подписка снимается сервером. Само событие до него не доходит. Клиенту следует
считать тему потерянной: перечитать данные обычным запросом и показать то, что
он вернёт (для чужого проекта это будет 404).

## 5. Каталог событий

Общая форма:

```json
{
  "type": "event",
  "topic": "issue:DEV-42",
  "event": "comment.created",
  "at": "2026-09-09T10:15:30.412Z",
  "actorId": "0f1e2d3c-4b5a-6978-8796-a5b4c3d2e1f0",
  "data": { "…": "…" }
}
```

`actorId` — кто вызвал событие; `null` у системных. Своё же действие возвращается
и инициатору: по `actorId` его отличают от чужого и, например, не мигают подсветкой
«внешнее изменение» на собственную правку. `at` — момент публикации на сервере,
ISO-8601 UTC.

### Тема `issue:<KEY>`

| `event` | `data` | Что делать клиенту |
|---|---|---|
| `issue.updated` | `{ "key": "DEV-42", "changedFields": ["status","title"] }` | перечитать `GET /api/issues/{key}` (и `…/history`, если открыта вкладка истории) |
| `issue.deleted` | `{ "key": "DEV-42" }` | закрыть экран задачи, увести в очередь |
| `comment.created` | `{ "id": "<uuid>", "issueKey": "DEV-42" }` | подтянуть ленту комментариев |
| `comment.updated` | `{ "id": "<uuid>", "issueKey": "DEV-42" }` | перечитать этот комментарий |
| `comment.deleted` | `{ "id": "<uuid>", "issueKey": "DEV-42" }` | убрать комментарий из ленты |

`changedFields` содержит имена полей **так, как они называются в ответе
`GET /api/issues/{key}`**:

`title`, `description`, `status`, `priority`, `storyPoints`, `author`, `assignee`,
а также `links` (внешние ссылки) и `attachments` (вложения).

Любое из этих событий означает, что **история задачи тоже могла измениться**:
отдельного события у истории нет.

Пример:

```json
{
  "type": "event",
  "topic": "issue:DEV-42",
  "event": "issue.updated",
  "at": "2026-09-09T10:15:30.412Z",
  "actorId": "0f1e2d3c-4b5a-6978-8796-a5b4c3d2e1f0",
  "data": { "key": "DEV-42", "changedFields": ["status"] }
}
```

### Тема `project:<slug>`

| `event` | `data` |
|---|---|
| `project.member_joined` | `{ "userId": "<uuid>", "role": "member" }` |
| `project.member_updated` | `{ "userId": "<uuid>", "role": "admin" }` |
| `project.member_removed` | `{ "userId": "<uuid>" }` |

Имена полей совпадают с `ProjectMemberDto` (`userId`, `role`). Исключённому
участнику `project.member_removed` про него самого **не придёт**: право проверяется
при рассылке, а он уже не участник. О своём исключении он узнаёт обычным запросом.

### Тема `user:me`

| `event` | `data` |
|---|---|
| `notification.created` | `{ "id": "<uuid>", "type": "issue_commented", "unreadCount": 3 }` |
| `notification.read` | `{ "unreadCount": 0 }` |

`type` — значение из перечисления `NotificationDto.type`. `unreadCount` — то же
число, что отдаёт `GET /api/notifications/unread-count`; отдельный запрос ради
счётчика делать не нужно.

`notification.read` приходит, когда пользователь прочитал уведомления **в другой
вкладке или на другом устройстве**: счётчик в шапке должен уменьшиться.

Пример:

```json
{
  "type": "event",
  "topic": "user:me",
  "event": "notification.created",
  "at": "2026-09-09T10:15:30.412Z",
  "actorId": "0f1e2d3c-4b5a-6978-8796-a5b4c3d2e1f0",
  "data": { "id": "8c3b…", "type": "issue_mentioned", "unreadCount": 3 }
}
```

### Чего в протоколе нет намеренно

- **Событий по спискам задач и по доске.** D-26 их не покрывает, а поток изменений
  по всей очереди дороже пользы.
- **Полного тела задачи или комментария в событии.** Ответ REST собирается под
  конкретного запросившего — его роль и права, — и у разных подписчиков он разный.
  Рассылать «общий» вариант значило бы завести второй формат тех же данных.
- **Гарантий порядка и доставки.** Порядок событий в одной теме соблюдается, пока
  жив сокет, но пропуск возможен. Не стройте на событиях состояние — стройте
  на них решение «перечитать вот это».

## 6. Живость соединения и переподключение

- **Сервер** каждые `heartbeatSeconds` (30) шлёт кадр протокола `ping`. Браузер
  отвечает на него сам; отдельного кода писать не нужно. Соединение, не ответившее
  за один такт, обрывается.
- **Клиент** для собственной проверки шлёт прикладной `{"type":"ping"}` и ждёт
  `pong`: браузерный JS кадров протокола не видит и иначе не заметит, что сервер
  перестал отвечать.
- Тем же тактом сервер перепроверяет сессию: погашенная закрывает сокет кодом
  `4401`, даже если служебное сообщение об этом потерялось.

### Коды закрытия

| Код | Значение | Что делать |
|---|---|---|
| `4401` | сессия истекла или погашена | не переподключаться, уйти на `/login` |
| `4403` | доступ к трекеру отозван (US-09) или пользователь вышел (US-03) | не переподключаться, уйти на экран отказа/входа |
| `4499` | сервер выключается | переподключиться с задержкой |
| `1006`, `1001` и прочие сетевые | обрыв | переподключиться с экспоненциальной задержкой |

Коды `4401` и `4403` — окончательные: цикл переподключения на них останавливается,
иначе клиент будет молотить сервер после выхода пользователя.

### Как переподключаться

Состояние подписок живёт **в соединении**: закрылся сокет — на сервере не осталось
ничего. Поэтому переподключение — это всегда «как в первый раз»:

1. открыть сокет заново;
2. дождаться `ready`;
3. подписаться на все темы, которые нужны открытым экранам;
4. **перечитать данные этих экранов обычными запросами** — за время обрыва события
   были потеряны.

Пункт 4 обязателен: без него после потери сети экран останется устаревшим, и это
будет выглядеть как исчезнувшие комментарии.

## 7. Ограничения

| Что | Предел |
|---|---|
| Тем на одно соединение | 20 (`maxTopics` в кадре `ready`) |
| Размер кадра от клиента | 8 КБ; больший обрывается кодом `1006`/`1009` на уровне библиотеки |
| Длина ярлыка темы | 128 символов |
| Длина `id` команды | 64 символа |

Соединений на пользователя не ограничено: несколько вкладок — обычное дело.

## 8. Безопасность

- Секрет сессии в кадрах не передаётся **никогда**: он предъявляется один раз,
  на рукопожатии. Идентификатор сессии наружу тоже не уходит ни в одном кадре.
- Cookie-соединение требует совпадения `Origin`: без этого чужая страница могла бы
  открыть сокет от имени вошедшего пользователя (cross-site WebSocket hijacking) —
  cookie браузер к рукопожатию приложит сам.
- Несуществующая и недоступная тема отвечают одинаково (`topic_forbidden`): по
  ответу нельзя узнать, существует ли чужая задача или проект (permissions.md, п. 5).
- Отзыв доступа к трекеру закрывает открытые сокеты немедленно, на всех экземплярах
  API, — так же, как гасит сессии (ADR-0006).

## 9. Пример: экран задачи

```js
const socket = new WebSocket(`wss://${location.host}/api/ws`);

socket.addEventListener('message', (message) => {
  const frame = JSON.parse(message.data);

  if (frame.type === 'ready') {
    socket.send(JSON.stringify({ type: 'subscribe', id: 'issue', topic: `issue:${issueKey}` }));
    return;
  }

  if (frame.type === 'subscribed') {
    // Канонический ярлык — сравнивать события надо с ним.
    topics.set(frame.id, frame.topic);
    return;
  }

  if (frame.type === 'error' && frame.code === 'topic_forbidden') {
    // Права потеряны прямо сейчас: перечитать экран и показать, что вернёт сервер.
    reload();
    return;
  }

  if (frame.type !== 'event') return;

  switch (frame.event) {
    case 'issue.updated':
      reloadIssue(frame.data.changedFields);
      break;
    case 'issue.deleted':
      leaveToQueue();
      break;
    case 'comment.created':
    case 'comment.updated':
    case 'comment.deleted':
      reloadComments();
      break;
    case 'notification.created':
    case 'notification.read':
      setUnreadCount(frame.data.unreadCount);
      break;
  }
});
```

`frame.actorId === currentUserId` — своё действие: подсветку «внешнее изменение»
(issue.md, «Поведение») на него ставить не нужно, а набранный текст сбрасывать
нельзя ни в каком случае (US-45).
