## 1. Что проверяем и зачем именно так

Бэкенд и клиент закрыты своими тестами: 256 unit и 270 e2e на API, 320 тестов на клиенте.
Эти тесты проверяют **части**. Их сильная сторона — изоляция: каждый тест поднимает своё
состояние и проверяет одну вещь. Она же — их слепое пятно.

Сквозной слой в `e2e/` существует ради того, что из изоляции не видно:

1. **Состояние между запросами.** Пригласили → принял → появился в участниках → назначили
   исполнителем → увидел в сайдбаре → исключили → исполнитель обнулился, задача осталась,
   уведомления прекратились. Каждый шаг по отдельности верен, ломается стык.
2. **Два клиента одновременно.** Требование D-26 — «изменение доходит до другого пользователя
   не позднее чем через 5 секунд» — по определению нельзя проверить одним клиентом.
3. **Живой сокет и отзыв доступа.** Открытая вкладка, которой гасят сессию, — это состояние,
   которого внутри Jest не существует.
4. **Гонки на уровне HTTP.** Параллельная выдача ключей задач проверена в API вызовами
   сервиса; через HTTP в игру входят разбор тела, пул соединений и транзакция запроса целиком.
5. **Соответствие опубликованному контракту.** В e2e бэкенда ожидаемый код ответа пишется
   рядом с кодом контроллера и повторяет реализацию. Расхождение с `docs/api/openapi.json`
   так не ловится, а платит за него генерируемый клиент Flutter.

## 2. Чем проверяем

| Что | Решение | Почему так |
|---|---|---|
| Раннер | встроенный в Node `node --test` | Прогон идёт **против живого API по HTTP**, а не против приложения, собранного внутри процесса. Jest здесь не даёт ничего: ни трансформации TypeScript, ни моков не нужно. Ноль зависимостей сверх необходимого и ноль конфигурации |
| HTTP | встроенный `fetch` | Клиент ведёт себя как браузер: cookie `sl_session` и заголовок `Origin` на небезопасных методах |
| WebSocket | пакет `ws` | Рукопожатию нужны заголовки `Cookie` и `Origin`. Браузер ставит их сам, встроенный в Node `WebSocket` задавать их не умеет, а без них соединение не открывается вовсе |
| База | пакет `pg` | Только для того, чего снаружи не сделать: выдать сессию и заглянуть в `sessions.revoked_at` |
| Redis | пакет `ioredis` | Только для сброса счётчиков ограничения частоты между сценариями |
| Запуск | `cd e2e && npm test` | `run.mjs` сам поднимает API, ждёт `/api/health`, чистит базу, гоняет тесты и гасит API |

Два флага раннера стоят осознанно. `--test-timeout` (по умолчанию 120 с на тест): зависший
тест обязан упасть с указанием места, иначе прогон не даёт ответа вообще. `--test-force-exit`:
без него набор встаёт на три минуты после каждого файла, который много ходил по HTTP —
`fetch` держит соединения в пуле keep-alive, процесс файла из-за них не завершается,
а раннер ждёт его завершения. Закрыть пул из теста нечем: Node не отдаёт наружу диспетчер
своего `fetch`. С флагами весь набор проходит за ~35 секунд.

### Как тесты получают сессию

Вход через Яндекс ID автоматизировать нельзя: он требует живого согласия человека
в интерфейсе Яндекса. Обходной путь выбран так, чтобы **не менять продуктовый код**.

Харнесс выпускает сессию сам, тем же способом, что и `SessionService.create`: пишет строку
в таблицу `sessions`, где `token_hash = HMAC-SHA256(verifier, SESSION_SECRET)`, и предъявляет
секрет вида `<sessionId>.<verifier>` (см. `apps/api/src/sessions/session-token.ts`).
`SessionService.resolve` не находит её в Redis, поднимает из PostgreSQL и кэширует — дальше
она ничем не отличается от выданной настоящим входом, включая отзыв через `destroyAllForUser`.

**Тестовый эндпоинт в API не нужен и не предлагается.** Он добавил бы в боевой код путь
выдачи сессии без аутентификации — цена ошибки в таком коде несоизмерима с удобством.

### Изоляция от рабочего окружения

Три уровня, все обязательны:

| Ресурс | Рабочее | e2e бэкенда | Сквозные тесты |
|---|---|---|---|
| Порт API | 3000 | — (в процессе) | **3100** |
| База PostgreSQL | `sl_tracker` | `sl_tracker_test` | **`sl_tracker_e2e`** |
| Логическая база Redis | 0 | 15 | **14** |
| Bucket MinIO | `sl-attachments` | тот же | **`sl-tracker-e2e`** |

Своя база PostgreSQL нужна не только ради рабочих данных: e2e бэкенда делают `truncate`
всех таблиц, и общая с ними база означала бы, что чужой прогон сносит данные в середине
нашего сценария.

## 4. Граничные случаи, проверяемые всегда

- **Пусто:** нет проектов, очередей, задач, комментариев, вложений, приглашений, уведомлений.
  Ожидание — `items: []`, `total: 0`, `nextCursor: null`, а не ошибка и не `null` вместо списка.
- **Один и много:** 120 задач в очереди, 35 комментариев, 13 участников, 15 уведомлений —
  постраничный обход обязан вернуть всё, ровно по разу.
- **Границы длины:** последний допустимый символ проходит, следующий отклоняется.
  Название задачи 255/256, комментарий 10 000/10 001, описание 100 000/100 001.
- **Юникод:** кириллица, эмодзи (включая составные), RTL, комбинирующие диакритики,
  CJK, символы нулевой ширины и управляющие BiDi.
- **Похожее на инъекцию:** `'; drop table issues; --`, `<script>`, `${...}`, `%` и `_`
  (шаблон LIKE), обратные слеши. Хранится дословно, поиск по такой строке не ломается.
- **Нулевой символ** `U+0000` — отдельно: PostgreSQL не хранит его в `text`.
- **Одновременность:** правка одной задачи двумя людьми, двойная отправка, гонка
  «удаление задачи + запись в неё», спор за один ключ очереди.
- **Пределы:** `limit` = 0, −1, нечисловой, сверх максимума; испорченный и чужой курсор.

## 5. Вне объёма сквозного слоя

Названо явно: это не «проверено», это **не проверялось**, и вот почему.

| Что | Почему вне объёма | Кто закрывает |
|---|---|---|
| **Живой поток OAuth Яндекс ID** (`/auth/yandex/start` → Яндекс → `/callback`) | Требует согласия человека в интерфейсе Яндекса; автоматизировать нельзя. Сессия в тестах выдаётся в обход | Ручной вход (выполнен пользователем); подмена `state`, повторный `code`, `unauthorized_client` — в `apps/api/test/auth.e2e-spec.ts` |
| **Проверка «пускать ли в трекер»** (список доступа ИЛИ действующее приглашение) | Живёт внутри колбэка OAuth, до выдачи сессии. Харнесс выдаёт сессию после этой точки | `apps/api/test/auth.e2e-spec.ts`. Сквозной слой проверяет следствие: приглашённый без записи в списке доступа вступает в проект |
| **Интерфейс Flutter** | Сквозной слой ходит по API. Виджет-тесты и ручная проверка в браузере — отдельный контур | Клиентские тесты; ручной чек-лист |
| **Рендер Markdown и обезвреживание HTML** | Сервер разметку не обрабатывает намеренно (D-22); не исполнять её — обязанность клиента. Проверяется, что сервер хранит текст дословно | Клиент |
| **Тёмная схема, доступность, вид на узком экране** | Тема живёт целиком в клиенте: API о ней не знает, значений цвета по HTTP не отдаёт. Сквозной набор ходит по HTTP и увидеть схему не может **в принципе** — это не «руки не дошли» | Ручной чек-лист, [раздел 9](#9-тёмная-схема-ручной-чек-лист); виджет-тесты клиента |
| **Отзыв доступа на нескольких экземплярах API** | Стенд поднимает один экземпляр. Механизм — Redis pub/sub — тот же, что для событий, и он проверен | Проверять на боевом стенде при масштабировании |
| **Нагрузка и деградация под объёмом** | Проверяется корректность на 120 задачах, а не время отклика под нагрузкой | Отдельная задача, если появится требование |
| **Боевой стенд (порт 8443, Caddy, TLS)** | Собран после написания набора; прогон против него — отдельный заход через `E2E_EXTERNAL_API=1` | Оркестратор при деплое |
| **Письма и внешние каналы уведомлений** | Не входят в MVP (Q1) | — |

## 6. Как запускать

```bash
cd e2e
npm install          # один раз
npm test             # весь набор
node run.mjs tests/realtime.test.mjs   # один файл
E2E_API_LOG=1 node run.mjs             # с логом API — нужно при разборе 500
```

Требуется: поднятый `infra/compose/docker-compose.dev.yml` (PostgreSQL, Redis, MinIO),
собранный API (`cd apps/api && npm run build`) и `.env` в корне репозитория.
База `sl_tracker_e2e` создаётся один раз:

```bash
cd apps/api && POSTGRES_DB_OVERRIDE=sl_tracker_e2e npx drizzle-kit migrate
```

Переменные, которыми можно сдвинуть прогон: `E2E_API_PORT` (по умолчанию 3100),
`E2E_POSTGRES_DB`, `E2E_REDIS_DB`, `E2E_APP_BASE_URL`, `E2E_EXTERNAL_API=1` вместе
с `E2E_API_URL` — для прогона против уже запущенного стенда.

## 8. Что считаем провалом

- Любой ответ `500`. Ошибка сервера — это дефект, даже если случай экзотический:
  наружу не должно уходить необработанное исключение.
- Расхождение с `openapi.json` по коду ответа или форме тела.
- `403` там, где по permissions.md раздел 5 положен `404` (и наоборот).
- Событие живых обновлений, дошедшее до того, кто на него уже не имеет права.
- Задержка доставки события больше 5 секунд (D-26).
- Дубликат ключа задачи при любой параллельности.
- Запись в базе, оставшаяся без родителя, или объект в MinIO без строки в `attachments`.
- Тест, который зелёный при сломанном поведении. Каждый тест проверялся на то,
  что он краснеет: дефекты из `defects.md` найдены именно так.

## 9. Тёмная схема: ручной чек-лист

### 9.1. Почему руками

Схема живёт целиком в клиенте: выбор хранится в браузере (`sl.theme.mode`), API о теме
не знает и цветов по HTTP не отдаёт. Сквозной набор из `e2e/` ходит по HTTP — он не может
увидеть цвет в принципе, и никакая доработка набора этого не изменит.

Автоматизировать можно **часть**, и это не то же самое, что весь объём:

| Слой | Чем закрывается | Замечание |
|---|---|---|
| Значения и контрасты пар | скриптом дизайнера, уже посчитано | `system.md` 12: ноль провалов, минимум 5.08:1 при требовании 4.5 |
| Компоненты дизайн-системы | golden-тесты в обеих схемах | только для **стабильных** компонентов: golden на живой экран превращается в источник ложных падений, и его начинают переутверждать не глядя |
| Экраны целиком, в состояниях | **только человек** | состояния наведения, фокуса и загрузки на живых данных — это и есть предмет проверки |

Дальше — то, что должен пройти человек. Проверка идёт **на собранном вебе**
(`flutter build web --wasm`), а не в debug: в debug другой путь загрузки и первого кадра.

### 9.2. Как проходить

1. Профиль → секция «Оформление» — переключатель темы (`screens/profile.md`).
   Проверяются все три положения: «Системная», «Светлая», «Тёмная».
2. Каждый экран из таблицы 9.3 открывается **дважды**: в светлой и в тёмной.
   Светлая — не формальность: правки темы ломают её ровно так же.
3. На каждом экране отдельно проверяются четыре состояния из 9.4.
   Их легко пропустить: они не видны на статичном скриншоте.
4. Находка описывается по формату из `defects.md` — с экраном, схемой, состоянием
   и шириной окна. «В тёмной некрасиво» дефектом не является.

Отметка о прогоне ставится в отчёте: экран, схема, дата, кто прошёл.

- [ ] 1. Оболочка приложения — сайдбар, шапка, поиск, счётчик активных задач
- [ ] 2. Вход `/login` — **особое место, см. 9.5**
- [ ] 3. Доступ закрыт `/access-denied`
- [ ] 4. Мои проекты `/`
- [ ] 5. Проект `/projects/<slug>`
- [ ] 6. Список задач очереди `/queues/<KEY>` — таблица, плашки статусов, приоритеты
- [ ] 7. Задача `/issues/<KEY>-<N>` — разметка, упоминания, вложения, история
- [ ] 8. Приём приглашения `/invite/<token>`
- [ ] 9. Центр уведомлений `/notifications`
- [ ] 10. Профиль `/me` — здесь же сам переключатель

Ширины: достаточно `lg` (1024–1439) для всех и дополнительно `sm` (< 768) для экранов

### 9.4. Четыре состояния на каждом экране

Требование дизайнера: проверяются отдельно, а не «заодно».

**Наведение.** Курсор на строке таблицы, кнопке, ссылке, элементе сайдбара, вкладке.

- [ ] изменение видно — но не как «другой элемент»: в тёмной схеме наложения
      *осветляют* подложку, в светлой затемняют (`system.md` 11)
- [ ] наведение на выделенную строку отличается от простого выделения
- [ ] наведение на акцентную кнопку не «съедает» надпись: в тёмной схеме заливка светлая,
      а текст на ней тёмный (`textOnAccent` — тёмные чернила, `system.md` 12.3)

**Фокус.** Только с клавиатуры: `Tab`, `Shift+Tab`, стрелки. Мышь не трогать.

- [ ] кольцо фокуса видно на **каждом** интерактивном элементе в обеих схемах
- [ ] фокус визуально отличается от наведения и от выделения (`accessibility.md` 2.2)
- [ ] кольцо не сливается с подложкой ни на одной поверхности: обычной, утопленной,
      выделенной строке, внутри модалки, на акцентной кнопке
- [ ] скрытая ссылка «Перейти к содержимому» при фокусе видна в обеих схемах
- [ ] в модалке фокус заперт внутри, `Esc` закрывает, фокус возвращается на вызвавший элемент

**Ошибка.** Проще всего воспроизвести, погасив API (или отключив сеть в devtools).

- [ ] экранная ошибка с кнопкой «Повторить» читаема в обеих схемах
- [ ] тост-ошибка: заливка, текст и граница различимы; тост-ошибка **не исчезает сама**
- [ ] поле формы с ошибкой: рамка и подпись видны, ошибка не закодирована одним цветом
      (рядом текст или значок — `accessibility.md`)
- [ ] `danger` в тёмной схеме — светлая заливка с тёмным текстом; надпись не пропала

**Скелетон.** Ловится на медленной сети (throttling в devtools) — иначе не успеть увидеть.

- [ ] скелетон в тёмной схеме — это `skeletonBase` `#242D3C`, а не светлая полоса
      на тёмном фоне и не «дыра»
- [ ] шиммер идёт в обеих схемах; при `prefers-reduced-motion` — статичная заливка
      без мерцания (`system.md` 11)
- [ ] геометрия скелетона повторяет реальный контент, и при подстановке данных
      ничего не «прыгает»
- [ ] проверить в нескольких местах: список задач, карточка задачи, лента комментариев,
      счётчик в сайдбаре, содержимое модалки

### 9.5. Точечные места

Здесь дизайнер сам отметил слабые места и решения, которые легко потерять при реализации
(`system.md` 12.4 и 12.6). Это самое вероятное место находок — смотреть прицельно.

- [ ] **Кнопка Яндекса на экране входа в тёмной схеме — белый вариант.** Чёрный даёт
      к фону `1.14:1`: единственный контрол единственного экрана без сессии превращается
      в прямоугольную дыру. Знак Яндекса не перекрашен ни в одной схеме
- [ ] **Первый кадр после перезагрузки в тёмной схеме — тёмный.** Белой вспышки нет.
      Отдельно проверить главный случай: тёмная схема выбрана явно **при светлой системе**
      (ключ `sl.theme.boot`, `system.md` 12.5). Проверять на собранном вебе
- [ ] **Переключение туда-обратно не оставляет артефактов** при открытых скелетоне,
      тултипе, тосте, модалке и выпадающем меню — все перерисовываются в новой схеме
- [ ] **Смена системной темы при открытом приложении** в режиме «Системная» применяется
      сразу, без перезагрузки. Явный выбор при этом системную смену игнорирует
- [ ] **Тултип в тёмной схеме не инвертируется** — он не белый прямоугольник
- [ ] **Пять плашек статусов** различаются не только светлотой (16.5–20.7 L*): текст
      статуса на месте всегда, тон и значок различимы
- [ ] **Плашка «открыт» на выделенной строке** (ΔL* 0.5): смысл несут текст и значок —
      проверить, что строка читается, а не «плашка исчезла»
- [ ] **Модалка**: при более слабой тени `shadowLg` от фона её отделяют граница и `scrim`
- [ ] **Переключатель** (трек против бегунка `1.92:1`): положение и подпись говорят
      о состоянии, цвет — не единственный признак
- [ ] **Скриншот списка задач в оттенках серого остаётся понятным** — быстрая проверка
      на то, что смысл нигде не держится на одном цвете
- [ ] **Доступность переключателя темы**: имя «Тема оформления», вариант «Системная»
      дополнен пояснением «сейчас тёмная» / «сейчас светлая»

### 9.6. Что считаем провалом здесь

- Нечитаемый текст или невидимая граница контрола в любой из схем.
- Невидимое кольцо фокуса хоть на одном интерактивном элементе.
- Состояние, отличимое **только** цветом.
- Белая вспышка при загрузке у пользователя тёмной схемы.
- Артефакт после переключения, не уходящий без перезагрузки.
- Цвет, оставшийся от другой схемы: захардкоженный `Color(0xFF…)` мимо темы.

## 10. Что усилить в наборе

Честный список долгов самого набора — не продукта.

**10.1. Форма и язык ошибки не проверяются (след DEF-04).** Тест
`ошибка 400 несёт машиночитаемый код` проверяет наличие строкового `code`, но не то,
что `message` — строка, а не массив, и что текст русский. Возврат к массиву или
к английской фразе библиотеки набор **не поймает**. Усиление — на два assert в том же
подтесте: `typeof response.body.message === 'string'` и отсутствие латиницы в тексте.

**10.2. Осиротевшие объекты в MinIO не проверяются автоматически (след DEF-02).**
Хранилищную половину дефекта QA закрывал руками, считая объекты до и после прогона.
В наборе есть проверка осиротевших **строк**, но не объектов. Чтобы закрыть тестом,
харнессу нужен доступ к S3 (`@aws-sdk/client-s3` в зависимостях `e2e/`) и проверка
«каждому объекту в bucket соответствует строка в `attachments`».

**10.3. Раннер не чистит bucket между прогонами** (Н-5 в `defects.md`). Из-за этого
абсолютное число объектов в хранилище ничего не значит, и мерить приходится разницей.
Чинится в `run.mjs` там же, где чистится база.

Все три — зона QA. В заход по закрытию реестра не делались намеренно: объём был
«закрыть дефекты и проверить», а не «переписать набор».
