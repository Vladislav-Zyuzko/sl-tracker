## 1. Что проверяем и зачем именно так

Бэкенд и клиент закрыты своими тестами: 256 unit и 270 e2e на API, 320 тестов на клиенте.
Эти тесты проверяют **части**. Их сильная сторона — изоляция: каждый тест поднимает своё
состояние и проверяет одну вещь. Она же — их слепое пятно.

Сквозной слой в `e2e/` существует ради того, что из изоляции не видно:

1. **Состояние между запросами.** Пригласили → принял → появился в участниках → назначили
   исполнителем → увидел в сайдбаре → исключили → исполнитель обнулился, задача осталась,
   уведомления прекратились. Каждый шаг по отдельности верен, ломается стык.
2. **Два клиента одновременно.** Требование D-26 — «изменение доходит до другого пользователя
   не позднее чем через 5 секунд» — по определению нельзя проверить одним клиентом.
3. **Живой сокет и отзыв доступа.** Открытая вкладка, которой гасят сессию, — это состояние,
   которого внутри Jest не существует.
4. **Гонки на уровне HTTP.** Параллельная выдача ключей задач проверена в API вызовами
   сервиса; через HTTP в игру входят разбор тела, пул соединений и транзакция запроса целиком.
5. **Соответствие опубликованному контракту.** В e2e бэкенда ожидаемый код ответа пишется
   рядом с кодом контроллера и повторяет реализацию. Расхождение с `docs/api/openapi.json`
   так не ловится, а платит за него генерируемый клиент Flutter.

## 2. Чем проверяем

| Что | Решение | Почему так |
|---|---|---|
| Раннер | встроенный в Node `node --test` | Прогон идёт **против живого API по HTTP**, а не против приложения, собранного внутри процесса. Jest здесь не даёт ничего: ни трансформации TypeScript, ни моков не нужно. Ноль зависимостей сверх необходимого и ноль конфигурации |
| HTTP | встроенный `fetch` | Клиент ведёт себя как браузер: cookie `sl_session` и заголовок `Origin` на небезопасных методах |
| WebSocket | пакет `ws` | Рукопожатию нужны заголовки `Cookie` и `Origin`. Браузер ставит их сам, встроенный в Node `WebSocket` задавать их не умеет, а без них соединение не открывается вовсе |
| База | пакет `pg` | Только для того, чего снаружи не сделать: выдать сессию и заглянуть в `sessions.revoked_at` |
| Redis | пакет `ioredis` | Только для сброса счётчиков ограничения частоты между сценариями |
| Запуск | `cd e2e && npm test` | `run.mjs` сам поднимает API, ждёт `/api/health`, чистит базу, гоняет тесты и гасит API |

Два флага раннера стоят осознанно. `--test-timeout` (по умолчанию 120 с на тест): зависший
тест обязан упасть с указанием места, иначе прогон не даёт ответа вообще. `--test-force-exit`:
без него набор встаёт на три минуты после каждого файла, который много ходил по HTTP —
`fetch` держит соединения в пуле keep-alive, процесс файла из-за них не завершается,
а раннер ждёт его завершения. Закрыть пул из теста нечем: Node не отдаёт наружу диспетчер
своего `fetch`. С флагами весь набор проходит за ~35 секунд.

### Как тесты получают сессию

Вход через Яндекс ID автоматизировать нельзя: он требует живого согласия человека
в интерфейсе Яндекса. Обходной путь выбран так, чтобы **не менять продуктовый код**.

Харнесс выпускает сессию сам, тем же способом, что и `SessionService.create`: пишет строку
в таблицу `sessions`, где `token_hash = HMAC-SHA256(verifier, SESSION_SECRET)`, и предъявляет
секрет вида `<sessionId>.<verifier>` (см. `apps/api/src/sessions/session-token.ts`).
`SessionService.resolve` не находит её в Redis, поднимает из PostgreSQL и кэширует — дальше
она ничем не отличается от выданной настоящим входом, включая отзыв через `destroyAllForUser`.

**Тестовый эндпоинт в API не нужен и не предлагается.** Он добавил бы в боевой код путь
выдачи сессии без аутентификации — цена ошибки в таком коде несоизмерима с удобством.

### Изоляция от рабочего окружения

Три уровня, все обязательны:

| Ресурс | Рабочее | e2e бэкенда | Сквозные тесты |
|---|---|---|---|
| Порт API | 3000 | — (в процессе) | **3100** |
| База PostgreSQL | `sl_tracker` | `sl_tracker_test` | **`sl_tracker_e2e`** |
| Логическая база Redis | 0 | 15 | **14** |
| Bucket MinIO | `sl-attachments` | тот же | **`sl-tracker-e2e`** |

Своя база PostgreSQL нужна не только ради рабочих данных: e2e бэкенда делают `truncate`
всех таблиц, и общая с ними база означала бы, что чужой прогон сносит данные в середине
нашего сценария.

## 3. Объём: критерии приёмки → проверки

Каждый шаг критерия готовности MVP (vision.md раздел 4) закрыт подтестом
в `e2e/tests/mvp-journey.test.mjs`, в том же порядке.

| # | Шаг критерия готовности | Где проверяется |

| 1 | Войти через Яндекс ID, владелец — из списка доступа | шаг 1; сам поток OAuth — вне объёма, см. раздел 5 |
| 2 | Создать проект | шаг 2 |
| 3 | Пригласить двоих по ссылке, приглашённых нет в списке доступа | шаг 3 |
| 4 | Создать очередь, пять статусов из коробки | шаг 4 |
| 5 | Завести 20 задач | шаг 5 |
| 6 | Назначить исполнителей | шаг 6 |
| 7 | Провести задачу по всем пяти статусам | шаг 7 |
| 8 | Обсудить в комментариях, позвать упоминанием | шаги 8, 9 |
| 9 | Увидеть свои активные задачи в сайдбаре, найти поиском | шаг 10 |
| 10 | Получить уведомления о назначении и об упоминании | шаг 11 |
| 11 | Посмотреть историю изменений | шаг 12 |
| 12 | Адрес проекта и ссылка на задачу открываются у коллеги | шаг 13 |
| 13 | Добавить человека в список доступа | шаг 14 |
| 14 | Отозвать доступ, открытая вкладка перестала показывать данные | шаг 15 и `access-revocation.test.mjs` |

### Состав набора

## 4. Граничные случаи, проверяемые всегда

- **Пусто:** нет проектов, очередей, задач, комментариев, вложений, приглашений, уведомлений.
  Ожидание — `items: []`, `total: 0`, `nextCursor: null`, а не ошибка и не `null` вместо списка.
- **Один и много:** 120 задач в очереди, 35 комментариев, 13 участников, 15 уведомлений —
  постраничный обход обязан вернуть всё, ровно по разу.
- **Границы длины:** последний допустимый символ проходит, следующий отклоняется.
  Название задачи 255/256, комментарий 10 000/10 001, описание 100 000/100 001.
- **Юникод:** кириллица, эмодзи (включая составные), RTL, комбинирующие диакритики,
  CJK, символы нулевой ширины и управляющие BiDi.
- **Похожее на инъекцию:** `'; drop table issues; --`, `<script>`, `${...}`, `%` и `_`
  (шаблон LIKE), обратные слеши. Хранится дословно, поиск по такой строке не ломается.
- **Нулевой символ** ` ` — отдельно: PostgreSQL не хранит его в `text`.
- **Одновременность:** правка одной задачи двумя людьми, двойная отправка, гонка
  «удаление задачи + запись в неё», спор за один ключ очереди.
- **Пределы:** `limit` = 0, −1, нечисловой, сверх максимума; испорченный и чужой курсор.

## 5. Вне объёма сквозного слоя

Названо явно: это не «проверено», это **не проверялось**, и вот почему.

| Что | Почему вне объёма | Кто закрывает |
|---|---|---|
| **Живой поток OAuth Яндекс ID** (`/auth/yandex/start` → Яндекс → `/callback`) | Требует согласия человека в интерфейсе Яндекса; автоматизировать нельзя. Сессия в тестах выдаётся в обход | Ручной вход (выполнен пользователем); подмена `state`, повторный `code`, `unauthorized_client` — в `apps/api/test/auth.e2e-spec.ts` |
| **Проверка «пускать ли в трекер»** (список доступа ИЛИ действующее приглашение) | Живёт внутри колбэка OAuth, до выдачи сессии. Харнесс выдаёт сессию после этой точки | `apps/api/test/auth.e2e-spec.ts`. Сквозной слой проверяет следствие: приглашённый без записи в списке доступа вступает в проект |
| **Интерфейс Flutter** | Сквозной слой ходит по API. Виджет-тесты и ручная проверка в браузере — отдельный контур | Клиентские тесты; ручной чек-лист |
| **Рендер Markdown и обезвреживание HTML** | Сервер разметку не обрабатывает намеренно (D-22); не исполнять её — обязанность клиента. Проверяется, что сервер хранит текст дословно | Клиент |
| **Тёмная тема, доступность, вид на узком экране** | Вне MVP либо вне API | Дизайнер и клиент |
| **Отзыв доступа на нескольких экземплярах API** | Стенд поднимает один экземпляр. Механизм — Redis pub/sub — тот же, что для событий, и он проверен | Проверять на боевом стенде при масштабировании |
| **Нагрузка и деградация под объёмом** | Проверяется корректность на 120 задачах, а не время отклика под нагрузкой | Отдельная задача, если появится требование |
| **Боевой стенд (порт 8443, Caddy, TLS)** | Собран после написания набора; прогон против него — отдельный заход через `E2E_EXTERNAL_API=1` | Оркестратор при деплое |
| **Письма и внешние каналы уведомлений** | Не входят в MVP (Q1) | — |

## 6. Как запускать

```bash
cd e2e
npm install          # один раз
npm test             # весь набор
node run.mjs tests/realtime.test.mjs   # один файл
E2E_API_LOG=1 node run.mjs             # с логом API — нужно при разборе 500
```

Требуется: поднятый `infra/compose/docker-compose.dev.yml` (PostgreSQL, Redis, MinIO),
собранный API (`cd apps/api && npm run build`) и `.env` в корне репозитория.
База `sl_tracker_e2e` создаётся один раз:

```bash
cd apps/api && POSTGRES_DB_OVERRIDE=sl_tracker_e2e npx drizzle-kit migrate
```

Переменные, которыми можно сдвинуть прогон: `E2E_API_PORT` (по умолчанию 3100),
`E2E_POSTGRES_DB`, `E2E_REDIS_DB`, `E2E_APP_BASE_URL`, `E2E_EXTERNAL_API=1` вместе
с `E2E_API_URL` — для прогона против уже запущенного стенда.

## 7. Состояние на 2026-09-10

Прогон всего набора: **265 проверок, 246 зелёных, 19 красных, 35 секунд**.
Все 19 красных — это пять дефектов из [defects.md](./defects.md) (14 листовых проверок
плюс 5 родительских тестов). Ничего другого не падает.

Ключевые измерения:

| Что | Требование | Факт |
|---|---|---|
| Комментарий доходит до второго клиента | ≤ 5 с (D-26) | 37 мс |
| Смена статуса доходит до второго клиента | ≤ 5 с (D-26) | 29 мс |
| Счётчик непрочитанных доходит до второго клиента | ≤ 5 с (D-26) | 17 мс |
| Сокет закрывается при отзыве доступа | «немедленно» (US-09) | 20 мс, код 4403 |
| Сокет закрывается при выходе | — | 17 мс, код 4403 |
| 30 одновременных созданий задач в одной очереди | ключи различны | 30 из 30 различны, номера 1..30 без дыр |
| Предел тем на соединение | 20 (`maxTopics`) | 19 своих + `user:me`, дальше `too_many_topics` |

## 8. Что считаем провалом

- Любой ответ `500`. Ошибка сервера — это дефект, даже если случай экзотический:
  наружу не должно уходить необработанное исключение.
- Расхождение с `openapi.json` по коду ответа или форме тела.
- `403` там, где по permissions.md раздел 5 положен `404` (и наоборот).
- Событие живых обновлений, дошедшее до того, кто на него уже не имеет права.
- Задержка доставки события больше 5 секунд (D-26).
- Дубликат ключа задачи при любой параллельности.
- Запись в базе, оставшаяся без родителя, или объект в MinIO без строки в `attachments`.
- Тест, который зелёный при сломанном поведении. Каждый тест проверялся на то,
  что он краснеет: дефекты из `defects.md` найдены именно так.
