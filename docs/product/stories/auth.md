# Вход, сессия и доступ в трекер (US-01 … US-09)

Блок 1 MVP. Термины — [glossary.md](../glossary.md), права — [permissions.md](../permissions.md).
Технический поток OAuth зафиксирован в `CLAUDE.md` (весь обмен с Яндексом идёт через бэкенд,
фронт токенов Яндекса не видит) — здесь описывается только наблюдаемое поведение.

---

## US-01. Вход через Яндекс ID

**Как** человек, которому дали доступ к трекеру,
**я хочу** входить одним нажатием через свой Яндекс-аккаунт,
**чтобы** не заводить и не запоминать ещё один пароль.

*Если этого нет:* пользоваться продуктом невозможно вообще — весь трекер за авторизацией.

### Критерии приёмки
- [ ] Неаутентифицированный пользователь, открывший любой адрес приложения, видит экран входа
      с единственной кнопкой «Войти через Яндекс».
- [ ] Нажатие кнопки уводит пользователя на страницу Яндекс ID; после подтверждения он
      возвращается в приложение уже вошедшим.
- [ ] После первого **разрешённого** входа (см. US-05) в трекере создан пользователь с именем,
      email и аватаром из данных Яндекс ID; повторный вход тем же аккаунтом **не** создаёт
      второго пользователя.
- [ ] Если пользователь отказался выдать доступ на стороне Яндекса, он возвращается на экран
      входа с сообщением «Вход отменён» и возможностью попробовать снова; аккаунт не создаётся.
- [ ] Если вход не удался по технической причине, показывается сообщение об ошибке с
      предложением повторить; экран не остаётся пустым и не зависает в загрузке.
- [ ] Пользователь, открывший ссылку на задачу без сессии (`/issues/DEV-42`), после входа
      попадает **на эту задачу**, а не на главный экран.
- [ ] Имя и аватар обновляются из Яндекс ID при каждом входе (пользователь сменил аватар —
      после следующего входа в трекере новый).

### Не входит в объём
- Вход по email и паролю — не в MVP ([vision.md](../vision.md), решение пользователя).
- Другие провайдеры входа, привязка нескольких аккаунтов к одному пользователю.
- Ограничение на то, кто может войти, описано отдельно: US-05 и US-06.

## US-02. Сохранение сессии между визитами

**Как** пользователь трекера
**я хочу** оставаться вошедшим при возврате в приложение,
**чтобы** не проходить вход каждое утро.

*Если этого нет:* трекер перестаёт быть «вкладкой, открытой весь день».

### Критерии приёмки
- [ ] После закрытия и повторного открытия вкладки браузера пользователь остаётся вошедшим.
- [ ] Сессия живёт не меньше 30 дней при периодическом использовании.
- [ ] При истечении или отзыве сессии любое действие приводит к экрану входа с сообщением
      «Сессия истекла, войдите снова»; введённые, но не отправленные данные не теряются молча —
      пользователь получает предупреждение до перехода на экран входа.
- [ ] Открытие приложения в двух вкладках работает корректно: выход в одной вкладке приводит
      к экрану входа в другой при следующем действии.

### Не входит в объём
- Список активных сессий и «выйти на всех устройствах» — не в MVP.
- Двухфакторная аутентификация на нашей стороне (за неё отвечает Яндекс ID).

## US-03. Выход

**Как** пользователь, работающий с чужого или общего компьютера,
**я хочу** выйти из трекера,
**чтобы** мои задачи не увидел следующий человек.

### Критерии приёмки
- [ ] Пункт «Выйти» доступен из меню профиля на любом экране приложения.
- [ ] После выхода пользователь видит экран входа; возврат кнопкой «Назад» в браузере
      не показывает данные — открывается экран входа.
- [ ] После выхода прямой переход на `/issues/DEV-42` требует входа.
- [ ] Выход в трекере не завершает сессию пользователя в самом Яндексе.

### Не входит в объём
- Автоматический выход по бездействию.

---

## US-04. Профиль пользователя

**Как** пользователь
**я хочу** видеть, под кем я вошёл,
**чтобы** не перепутать рабочий и личный аккаунт.

### Критерии приёмки
- [ ] В шапке приложения постоянно видны аватар и имя текущего пользователя.
- [ ] На экране профиля показаны имя, email и аватар, полученные из Яндекс ID, и указано,
      что они меняются в аккаунте Яндекса, а не здесь.
- [ ] Поля профиля недоступны для редактирования в трекере.
- [ ] Если Яндекс ID не отдал имя и фамилию, отображаемым именем становится то, что провайдер
      всё-таки вернул: email или логин. Это ожидаемое поведение, а не дефект
      ([D-43](../decisions.md#d-43)); человек, которого такое имя не устраивает, заполняет
      имя в своём аккаунте Яндекса — после следующего входа трекер его подхватит (US-01).
- [ ] На экране профиля есть настройки уведомлений (см. [notifications](./notifications.md), US-103).
- [ ] На экране профиля есть выбор темы оформления: **как в системе** (по умолчанию),
      **светлая**, **тёмная** ([D-44](../decisions.md#d-44)). В режиме «как в системе» смена
      системной настройки перекрашивает приложение сразу, без перезагрузки страницы.
- [ ] Выбор темы сохраняется на этом устройстве и действует после перезагрузки страницы;
      на другом устройстве того же пользователя действует значение по умолчанию.

### Не входит в объём
- Редактирование имени и аватара внутри трекера, загрузка своей фотографии. Редактируемое
  отображаемое имя — кандидат в релиз 2, вопрос Q18 ([D-43](../decisions.md#d-43)).
- Перенос выбора темы между устройствами (тема хранится локально).
- Другие настройки оформления: акцентный цвет, плотность интерфейса, размер шрифта.
- Часовой пояс, язык интерфейса, иные персональные настройки.
- Удаление аккаунта пользователем.

## US-05. Доступ в трекер только по списку доступа

**Как** владелец трекера
**я хочу**, чтобы внутрь попадали только разрешённые люди,
**чтобы** трекер, открытый в интернет, не заполнился посторонними аккаунтами.

*Если этого нет:* любой владелец Яндекс-аккаунта заводит себе учётную запись на нашем VPS —
пусть и без доступа к проектам, но с возможностью создавать свои.

### Критерии приёмки
- [ ] После успешной аутентификации в Яндекс ID пользователь попадает внутрь приложения,
      только если выполняется хотя бы одно условие: его email есть в списке доступа
      **или** он пришёл по действующей ссылке-приглашению ([D-33](../decisions.md#d-33)).
- [ ] Пользователь, не удовлетворяющий ни одному условию, видит экран «Доступ к трекеру
      закрыт» с пояснением, что нужно приглашение от администратора проекта,
      и кнопкой «Выйти».
- [ ] Такому пользователю **не создаётся** учётная запись в трекере и **не выдаётся** сессия:
      повторное открытие приложения снова показывает экран входа.
- [ ] Экран отказа не раскрывает ничего о содержимом трекера: ни списка проектов,
      ни числа пользователей, ни имён администраторов.
- [ ] Любой запрос к API от пользователя, не прошедшего список доступа, отклоняется;
      машиночитаемый ответ — 403 с отдельным кодом причины (см. [permissions](../permissions.md), раздел 5).
- [ ] Пользователь, прошедший список доступа, но не состоящий ни в одном проекте, попадает
      в приложение и видит пустой список проектов с пояснением, как получить доступ
      к проекту, и возможностью создать свой.
- [ ] Проверка выполняется по email из данных Яндекс ID, без учёта регистра.
- [ ] Тот же экран «Доступ к трекеру закрыт» видит пользователь, чей доступ отозван (US-09):
      отдельного текста «вас удалили» нет, чтобы не раскрывать причину.

### Не входит в объём
- Ограничение по домену email (`@company.ru`) — команда работает с личных почт.
- Заявка на доступ («попросить разрешение») с уведомлением владельца.
- Ведение и редактирование списка описаны отдельно: US-06, US-07, US-09.

## US-06. Наполнение списка доступа

**Как** владелец трекера
**я хочу** понимать, откуда в списке доступа берутся записи,
**чтобы** впустить первых людей и не заводить каждого вручную.

### Критерии приёмки
- [ ] Начальное наполнение списка доступа приходит из конфигурации инстанса и применяется
      при запуске без изменения кода и пересборки клиента.
- [ ] Записи начального наполнения имеют источник «из конфигурации» и **автоматически**
      получают признак владельца трекера ([D-39](../decisions.md#d-39)) — иначе в свежем
      инстансе некому управлять доступом.
- [ ] Повторный запуск с той же конфигурацией не создаёт дубликаты записей.
- [ ] Удаление адреса из конфигурации **не** удаляет запись из списка: список — это данные,
      а не отражение конфигурации. Отзыв доступа делается на экране (US-09).
- [ ] При принятии приглашения email вступившего добавляется в список автоматически,
      с источником «по приглашению» и датой; признак владельца при этом не выдаётся.
- [ ] Повторное вступление того же человека по другому приглашению вторую запись не создаёт.
- [ ] Запись в списке доступа не даёт прав ни в одном проекте: доступ к проектам определяется
      только членством и ролью.
- [ ] Человек, добавленный в список любым способом, входит со следующей попытки — без
      перезапуска сервиса и без действий с его стороны, кроме входа.

### Не входит в объём
- Автоматическое добавление по домену email.
- Заявки на доступ и их рассмотрение.
- Ограничение числа пользователей, лицензии, тарифы.

## US-07. Экран управления списком доступа

**Как** владелец трекера
**я хочу** видеть и править список доступа в интерфейсе,
**чтобы** впускать новых сотрудников без входа по SSH на сервер.

*Если этого нет:* каждый наём и каждое увольнение превращаются в администрирование сервера,
и управление доступом становится тем, что откладывают «на потом».

### Критерии приёмки

**Просмотр**
- [ ] Экран «Доступ в трекер» открывается из меню профиля и виден **только владельцу трекера**;
      у остальных пункта меню нет, а прямой вызов API возвращает 403.
- [ ] Для каждой записи показаны: email, источник записи («из конфигурации», «добавлен
      вручную», «по приглашению»), дата добавления, кем добавлена (для добавленных вручную),
      признак владельца трекера и отметка, входил ли этот человек в трекер хотя бы раз.
- [ ] Если человек уже входил, рядом с email показаны его имя и аватар из Яндекс ID;
      если ещё ни разу — только email с пометкой «ещё не входил».
- [ ] Список отсортирован по дате добавления, сначала новые; при количестве записей больше
      экрана он подгружается порциями.
- [ ] Есть поиск по подстроке в email и имени.
- [ ] Пустого списка не бывает: в нём всегда есть как минимум текущий владелец, поэтому
      пустое состояние не проектируется. Если список всё же оказался пуст (повреждённые
      данные), экран показывает предупреждение и не даёт удалить последнюю запись.

**Добавление**
- [ ] Владелец добавляет запись, введя email; регистр значения не имеет, адрес нормализуется
      к нижнему регистру.
- [ ] Некорректный адрес не принимается: ошибка показывается у поля, запрос не уходит.
- [ ] Добавление адреса, который уже есть в списке, дубликата не создаёт: показывается
      сообщение «Этот адрес уже в списке», серверный ответ — 409.
- [ ] Добавленная запись получает источник «добавлен вручную», текущую дату и имя
      добавившего; признак владельца ей не выдаётся.
- [ ] Добавленный человек может войти сразу, без приглашения; проектов при этом не видит,
      пока его не пригласят.
- [ ] Добавление адреса не отправляет человеку никаких сообщений: почтового канала нет
      ([D-18](../decisions.md#d-18)), адрес трекера он получает от коллеги.

**Признак владельца**
- [ ] Владелец может выдать признак владельца любой записи списка и снять его с любой другой.
- [ ] Снять признак с последнего владельца нельзя: действие блокируется сообщением
      «В трекере должен остаться хотя бы один владелец», серверный ответ — 409.
- [ ] Снять признак с себя можно, только если есть другой владелец; сразу после этого экран
      «Доступ в трекер» становится недоступен, без перезагрузки страницы.
- [ ] Признак владельца не даёт доступа ни к одному проекту: список проектов у владельца
      остаётся прежним ([D-39](../decisions.md#d-39)).

### Не входит в объём
- История изменений списка доступа (кто кого и когда добавлял или удалял) — релиз 2.
- Приглашение по email прямо с этого экрана — требует почтового канала.
- Массовое добавление списком, импорт из файла, добавление по домену.
- Временный доступ с датой окончания.

## US-08. Упоминание постороннего не работает

> Вынесено отдельной историей, потому что это правило приватности, а не удобство ввода.
> Механика самого упоминания описана в [comments](./comments.md), US-74.

**Как** участник проекта
**я хочу**, чтобы подсказка упоминаний показывала только людей из этого проекта,
**чтобы** состав организации не утекал через выпадающий список.

*Если этого нет:* любой участник любого проекта, вводя `@а`, `@б`, `@в`, выясняет полный
состав компании в трекере.

### Критерии приёмки
- [ ] В подсказке по `@` отображаются только участники проекта, которому принадлежит задача,
      в любой роли; пользователи трекера, не состоящие в проекте, не появляются ни при каком
      запросе ([D-41](../decisions.md#d-41)).
- [ ] Проверяемо: пользователь трекера «Пётр Смирнов», не состоящий в проекте, не находится
      в подсказке ни по `@Пётр`, ни по `@Smirnov`, ни по его email.
- [ ] Текст `@ivan`, набранный вручную и не выбранный из подсказки, сохраняется как обычный
      текст: не подсвечивается, не становится ссылкой, уведомления не создаёт — независимо
      от того, существует ли такой пользователь в трекере.
- [ ] Сообщений вида «пользователь не найден» или «пользователь есть, но не в проекте»
      не показывается: по реакции интерфейса нельзя понять, существует ли такой человек.
- [ ] Попытка создать упоминание не-участника напрямую через API не создаёт ни связи
      упоминания, ни уведомления; текст при этом сохраняется без ошибки.
- [ ] Если упомянутый участник позже исключён из проекта, старое упоминание в тексте
      остаётся видимым, но новых уведомлений он не получает.

### Не входит в объём
- Приглашение человека в проект прямо из подсказки упоминаний.
- Упоминание групп и ролей (`@все`).
- Подсказка, показывающая всех пользователей трекера, — отвергнута решением пользователя
  ([D-41](../decisions.md#d-41)).

## US-09. Отзыв доступа в трекер

**Как** владелец трекера
**я хочу** закрыть человеку доступ одним действием и прямо сейчас,
**чтобы** уволившийся сотрудник перестал видеть рабочие задачи, не дожидаясь истечения
своей сессии.

*Если этого нет:* отзыв доступа существует только на бумаге — человек с открытой вкладкой
продолжает работать в трекере как ни в чём не бывало.

### Критерии приёмки

**Само действие**
- [ ] Владелец трекера удаляет запись из списка доступа; действие требует подтверждения
      в диалоге, где сказано, что человек немедленно потеряет доступ, а его комментарии,
      история и задачи останутся.
- [ ] После удаления запись исчезает из списка; впустить человека снова можно, добавив
      адрес заново (US-07).
- [ ] Удалить собственную запись нельзя: действие недоступно, серверный ответ — 409,
      сообщение объясняет, что владельца удаляет другой владелец
      ([D-39](../decisions.md#d-39)).
- [ ] Удалить запись последнего владельца трекера нельзя; серверный ответ — 409.
- [ ] Не-владелец не видит действия удаления; прямой вызов API возвращает 403.

**Что происходит с человеком**
- [ ] Все активные сессии этого пользователя завершаются немедленно — во всех вкладках
      и на всех устройствах ([D-40](../decisions.md#d-40)).
- [ ] В открытой вкладке следующее действие (переход, сохранение, автообновление) приводит
      к экрану «Доступ к трекеру закрыт», а уже отрисованные данные скрываются. Проверяемо:
      у пользователя открыта задача, владелец отзывает доступ — не позднее чем через 5 секунд
      вкладка показывает экран закрытого доступа без содержимого задачи.
- [ ] Несохранённый текст, который человек набирал, не отправляется; на экране отказа сказано,
      что несохранённые изменения потеряны.
- [ ] Повторный вход через Яндекс ID приводит на тот же экран «Доступ к трекеру закрыт»;
      учётная запись при этом не удаляется.
- [ ] Все запросы к API из старой сессии отклоняются (401), включая скачивание вложений
      по ранее полученным ссылкам.

**Что происходит с его данными**
- [ ] Комментарии, записи истории, авторство и созданные им задачи остаются без изменений,
      с его именем и аватаром; обезличивания не происходит.
- [ ] Членство в проектах сохраняется: человек остаётся в списках участников со своей ролью,
      назначения его исполнителем не снимаются ([D-40](../decisions.md#d-40)).
- [ ] Возврат доступа (повторное добавление адреса) возвращает человеку его проекты и задачи
      в прежнем виде; заново приглашать его не нужно.
- [ ] Приглашения, которые он создавал как администратор проекта, продолжают действовать;
      отозвать их может администратор проекта ([invitations](./invitations.md), US-22).

### Не входит в объём
- Автоматическое исключение из проектов и снятие с задач при отзыве доступа — это отдельная
  ручная операция администратора проекта.
- Пометка «доступ отозван» рядом с именем в списке участников и в выборе исполнителя —
  остаточный вопрос Q17.
- Временная блокировка без удаления записи, «заморозка» пользователя.
- Удаление пользователя и его данных из трекера.
