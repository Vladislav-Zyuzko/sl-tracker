# Вход и сессия (US-01 … US-04)

Блок 1 MVP. Термины — [glossary.md](../glossary.md), права — [permissions.md](../permissions.md).
Технический поток OAuth зафиксирован в `CLAUDE.md` (весь обмен с Яндексом идёт через бэкенд,
фронт токенов Яндекса не видит) — здесь описывается только наблюдаемое поведение.

---

## US-01. Вход через Яндекс ID

**Как** человек, которому дали доступ к трекеру,
**я хочу** входить одним нажатием через свой Яндекс-аккаунт,
**чтобы** не заводить и не запоминать ещё один пароль.

*Если этого нет:* пользоваться продуктом невозможно вообще — весь трекер за авторизацией.

### Критерии приёмки
- [ ] Неаутентифицированный пользователь, открывший любой адрес приложения, видит экран входа
      с единственной кнопкой «Войти через Яндекс».
- [ ] Нажатие кнопки уводит пользователя на страницу Яндекс ID; после подтверждения он
      возвращается в приложение уже вошедшим.
- [ ] После первого **разрешённого** входа (см. US-05) в трекере создан пользователь с именем,
      email и аватаром из данных Яндекс ID; повторный вход тем же аккаунтом **не** создаёт
      второго пользователя.
- [ ] Если пользователь отказался выдать доступ на стороне Яндекса, он возвращается на экран
      входа с сообщением «Вход отменён» и возможностью попробовать снова; аккаунт не создаётся.
- [ ] Если вход не удался по технической причине, показывается сообщение об ошибке с
      предложением повторить; экран не остаётся пустым и не зависает в загрузке.
- [ ] Пользователь, открывший ссылку на задачу без сессии (`/issues/DEV-42`), после входа
      попадает **на эту задачу**, а не на главный экран.
- [ ] Имя и аватар обновляются из Яндекс ID при каждом входе (пользователь сменил аватар —
      после следующего входа в трекере новый).

### Не входит в объём
- Вход по email и паролю — не в MVP ([vision.md](../vision.md), решение пользователя).
- Другие провайдеры входа, привязка нескольких аккаунтов к одному пользователю.
- Ограничение на то, кто может войти, описано отдельно: US-05 и US-06.

## US-02. Сохранение сессии между визитами

**Как** пользователь трекера
**я хочу** оставаться вошедшим при возврате в приложение,
**чтобы** не проходить вход каждое утро.

*Если этого нет:* трекер перестаёт быть «вкладкой, открытой весь день».

### Критерии приёмки
- [ ] После закрытия и повторного открытия вкладки браузера пользователь остаётся вошедшим.
- [ ] Сессия живёт не меньше 30 дней при периодическом использовании.
- [ ] При истечении или отзыве сессии любое действие приводит к экрану входа с сообщением
      «Сессия истекла, войдите снова»; введённые, но не отправленные данные не теряются молча —
      пользователь получает предупреждение до перехода на экран входа.
- [ ] Открытие приложения в двух вкладках работает корректно: выход в одной вкладке приводит
      к экрану входа в другой при следующем действии.

### Не входит в объём
- Список активных сессий и «выйти на всех устройствах» — не в MVP.
- Двухфакторная аутентификация на нашей стороне (за неё отвечает Яндекс ID).

## US-03. Выход

**Как** пользователь, работающий с чужого или общего компьютера,
**я хочу** выйти из трекера,
**чтобы** мои задачи не увидел следующий человек.

### Критерии приёмки
- [ ] Пункт «Выйти» доступен из меню профиля на любом экране приложения.
- [ ] После выхода пользователь видит экран входа; возврат кнопкой «Назад» в браузере
      не показывает данные — открывается экран входа.
- [ ] После выхода прямой переход на `/issues/DEV-42` требует входа.
- [ ] Выход в трекере не завершает сессию пользователя в самом Яндексе.

### Не входит в объём
- Автоматический выход по бездействию.

## US-04. Профиль пользователя

**Как** пользователь
**я хочу** видеть, под кем я вошёл,
**чтобы** не перепутать рабочий и личный аккаунт.

### Критерии приёмки
- [ ] В шапке приложения постоянно видны аватар и имя текущего пользователя.
- [ ] На экране профиля показаны имя, email и аватар, полученные из Яндекс ID, и указано,
      что они меняются в аккаунте Яндекса, а не здесь.
- [ ] Поля профиля недоступны для редактирования в трекере.
- [ ] На экране профиля есть настройки уведомлений (см. [notifications](./notifications.md), US-103).

### Не входит в объём
- Редактирование имени и аватара внутри трекера, загрузка своей фотографии.
- Часовой пояс, язык интерфейса, иные персональные настройки.
- Удаление аккаунта пользователем.

## US-05. Доступ в трекер только по списку доступа

**Как** владелец инстанса
**я хочу**, чтобы внутрь попадали только разрешённые люди,
**чтобы** трекер, открытый в интернет, не заполнился посторонними аккаунтами.

*Если этого нет:* любой владелец Яндекс-аккаунта заводит себе учётную запись на нашем VPS —
пусть и без доступа к проектам, но с возможностью создавать свои.

### Критерии приёмки
- [ ] После успешной аутентификации в Яндекс ID пользователь попадает внутрь приложения,
      только если выполняется хотя бы одно условие: его email есть в списке доступа
      **или** он пришёл по действующей ссылке-приглашению ([D-33](../decisions.md#d-33)).
- [ ] Пользователь, не удовлетворяющий ни одному условию, видит экран «Доступ к трекеру
      закрыт» с пояснением, что нужно приглашение от администратора проекта,
      и кнопкой «Выйти».
- [ ] Такому пользователю **не создаётся** учётная запись в трекере и **не выдаётся** сессия:
      повторное открытие приложения снова показывает экран входа.
- [ ] Экран отказа не раскрывает ничего о содержимом трекера: ни списка проектов,
      ни числа пользователей, ни имён администраторов.
- [ ] Любой запрос к API от пользователя, не прошедшего список доступа, отклоняется;
      машиночитаемый ответ — 403 с отдельным кодом причины (см. [permissions](../permissions.md), раздел 5).
- [ ] Пользователь, прошедший список доступа, но не состоящий ни в одном проекте, попадает
      в приложение и видит пустой список проектов с пояснением, как получить доступ
      к проекту, и возможностью создать свой.
- [ ] Проверка выполняется по email из данных Яндекс ID, без учёта регистра.

### Не входит в объём
- Ограничение по домену email (`@company.ru`) — команда работает с личных почт.
- Экран управления списком доступа внутри трекера — вопрос Q14, кандидат в релиз 2.
- Отзыв доступа к трекеру через интерфейс — вопрос Q16.
- Заявка на доступ («попросить разрешение») с уведомлением владельца.

## US-06. Ведение списка доступа

**Как** владелец инстанса
**я хочу** понимать, как список доступа наполняется,
**чтобы** впустить первых людей и не разбирать заявки вручную каждый день.

### Критерии приёмки
- [ ] Начальный список доступа задаётся владельцем инстанса **вне интерфейса приложения**
      (конфигурация инстанса) и применяется без изменения кода и пересборки клиента.
- [ ] При принятии приглашения email вступившего добавляется в список доступа автоматически,
      с сохранением источника записи («приглашение») и даты.
- [ ] Повторное вступление того же человека по другому приглашению не создаёт вторую запись.
- [ ] Запись в списке доступа не даёт прав ни в одном проекте: доступ к проектам
      определяется только членством и ролью.
- [ ] Исключение человека из всех проектов запись в списке доступа не удаляет: он по-прежнему
      может войти и увидит пустой список проектов (осознанное ограничение MVP,
      [D-33](../decisions.md#d-33), вопросы Q14 и Q16).
- [ ] Изменение списка доступа не требует перезапуска, о котором должен знать пользователь:
      человек, добавленный владельцем, входит со следующей попытки.

### Не входит в объём
- Интерфейс просмотра и редактирования списка, история изменений списка — релиз 2.
- Роль «администратор инстанса» внутри продукта.
- Ограничение числа пользователей, лицензии, тарифы.
