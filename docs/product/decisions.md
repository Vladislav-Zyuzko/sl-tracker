# Журнал продуктовых решений

Формат записи: контекст → решение → альтернативы → почему так → цена решения.
Источник: **П** — решение пользователя (не пересматривается без него), **PM** — решение
продакт-менеджера (пересматривается через этот журнал).

Дата записей D-01 … D-31: 2026-09-06 (первая редакция).
Дата записей D-32 … D-38 и пометок «подтверждено пользователем»: 2026-09-06,
вторая редакция — после ответов пользователя на все открытые вопросы
(см. [vision.md](./vision.md#7-ответы-пользователя-на-открытые-вопросы)).

<a id="d-01"></a>

## D-01. Иерархия: Проект → Очередь → Задача — **П**

**Решение.** Три уровня. Проект — контейнер доступа и команды. Очередь — контейнер задач
одного рода внутри проекта. Задача живёт ровно в одной очереди.

**Альтернативы.** (а) Двухуровневая модель как в Яндекс Трекере: очередь сразу верхний уровень,
проектов нет. (б) Плоские задачи с метками вместо очередей.

**Почему.** Команда ведёт несколько направлений; очередь как верхний уровень заставляет
дублировать состав участников в каждой очереди. Проект даёт одно место для команды и прав.

**Цена.** Лишний уровень навигации и лишний экран. Ключ задачи при этом не содержит проект —
см. D-02.

---

<a id="d-02"></a>

## D-02. Ключ очереди глобально уникален — **П**

**Решение.** Ключ очереди уникален на весь трекер, а не в пределах проекта. Ключ задачи
`DEV-42` однозначно определяет задачу, URL — `/issues/DEV-42`.

**Альтернативы.** Уникальность в пределах проекта и URL вида `/projects/<slug>/issues/DEV-42`.

**Почему.** Короткая ссылка, которую можно вставить в чат; ключ читается вслух; так же
устроен Яндекс Трекер.

**Цена.** Ключи заканчиваются: `DEV` займёт первый, кто успел, остальным придётся выбирать
`DEV2`/`WEBDEV`. При создании очереди нужна понятная ошибка «ключ занят» — при этом мы **не**
сообщаем, в каком проекте он занят (утечка информации о чужих проектах).

<a id="d-03"></a>

## D-03. Доступ только по явному членству в проекте — **П**

**Решение.** Никаких публичных проектов и доступа «по ссылке». Видит проект только участник.

**Альтернативы.** Публичные проекты в пределах инстанса; доступ по секретной ссылке.

**Почему.** Инстанс открыт в интернет. Даже после введения списка доступа ([D-33](#d-33))
внутри трекера остаются люди из разных команд, и публичность по умолчанию означала бы,
что рабочие задачи одной команды видит вся остальная.

**Цена.** Каждый новый человек требует явного действия администратора (приглашение) —
теперь дважды: приглашение и впускает в трекер, и добавляет в проект.

<a id="d-04"></a>

## D-04. Два разных механизма ссылок на проект — **П**

**Решение.** (а) «Скопировать адрес проекта» — обычный URL, только навигация, доступа не даёт.
(б) Ссылка-приглашение с токеном — даёт членство после входа через Яндекс ID.

**Альтернативы.** Один механизм: ссылка, которая одновременно и адрес, и приглашение.

**Почему.** Смешение — классический источник утечек: человек копирует «ссылку на задачу»
в общий чат и раздаёт доступ, не заметив этого.

**Цена.** Два разных элемента в UI, которые нужно отличать визуально и текстом. Задача дизайнера.

---

<a id="d-05"></a>

## D-05. Через приглашение нельзя выдать роль администратора — **PM**

**Решение.** В приглашении выбирается роль по умолчанию: участник или читатель.
Администратора назначает только действующий администратор вручную в списке участников.

**Альтернативы.** Разрешить любую роль в приглашении.

**Почему.** Утёкшая ссылка-приглашение не должна давать право удалить проект.

**Цена.** Лишний шаг при заведении второго администратора.

---

<a id="d-06"></a>

## D-06. Ключ очереди и ключ задачи неизменяемы — **PM**

**Решение.** После создания ключ очереди не редактируется; ключ задачи не меняется никогда.

**Альтернативы.** Разрешить переименование ключа очереди с массовым обновлением ключей задач.

**Почему.** Ключ — публичный идентификатор, он уже разошёлся по чатам, коммитам и закладкам
(принцип «ключ не врёт», [vision.md](./vision.md)). В Яндекс Трекере ключ очереди тоже
изменить нельзя ([документация](https://yandex.ru/support/tracker/ru/manager/edit-queue-general)).

**Цена.** Опечатку в ключе исправить нельзя — только создать новую очередь. Значит, форма
создания очереди должна показывать предпросмотр будущего ключа задачи (`DEV-1`) и требовать
осознанного ввода.

---

<a id="d-07"></a>

## D-07. Номер задачи — счётчик очереди, без переиспользования — **PM**

**Решение.** Номер выдаётся по возрастанию в пределах очереди. Удаление задачи не освобождает
номер. Пропуски в нумерации допустимы и не считаются дефектом.

**Альтернативы.** Плотная нумерация с переиспользованием освободившихся номеров.

**Почему.** Переиспользование означает, что старая ссылка однажды приведёт на другую задачу.
Это хуже, чем дырка в нумерации.

**Цена.** Придётся объяснить пользователям, почему после `DEV-7` идёт `DEV-9`.

---

<a id="d-08"></a>

## D-08. Статусы хранятся данными, экрана редактирования в MVP нет — **П**

**Решение.** У каждой очереди свой набор статусов в БД. При создании очереди создаются пять:
Открыт, В работе, Ревью, Тестирование, Закрыт. UI редактирования — вне MVP.

**Альтернативы.** Enum в коде (дёшево сейчас, дорогая миграция потом).

**Почему.** Самая частая ошибка трекеров на старте — зашитый enum статусов.

**Цена.** Чуть больше работы в модели данных и в API сразу; сейчас пользователь этого
не увидит.

---

<a id="d-09"></a>

## D-09. Категория статуса (`open` / `in_progress` / `done`) — **PM**

**Решение.** У каждого статуса есть категория. Она определяет, считается ли задача
завершённой, и через это — что такое «активная задача».

**Альтернативы.** Флаг `is_final` (булев). Или «закрытым считается статус с системным именем
`closed`».

**Почему.** Булева флага не хватит для будущей доски и группировок; привязка к имени `closed`
сломается, как только появится редактор статусов и кто-то заведёт «Отменён».

**Цена.** Ещё одно поле, которое в MVP никто не редактирует.

---

<a id="d-10"></a>

## D-10. Переходы между статусами свободные — **PM**

**Решение.** Из любого статуса очереди можно перейти в любой другой статус той же очереди.
Графа переходов и условий в MVP нет.

**Альтернативы.** Зашить линейный воркфлоу Открыт → В работе → Ревью → Тестирование → Закрыт
с возвратами.

**Почему.** Любой жёсткий граф на старте окажется неверным для половины сценариев
(«вернуть из тестирования сразу в работу», «закрыть как неактуальную»). Ограничения
без редактора ограничений — это ловушка.

**Цена.** Пользователь может поставить «нелогичный» статус. Приемлемо: история изменений
покажет, кто это сделал.

---

<a id="d-11"></a>

## D-11. Участник может менять любую задачу проекта — **PM**

**Решение.** Права на задачу определяются ролью в проекте, а не авторством. Исключение —
комментарии (свой текст) и удаление задачи (только администратор).

**Альтернативы.** «Менять можно только свои задачи и задачи, где ты исполнитель».

**Почему.** В команде 3–15 человек ограничение по авторству мешает: подхватить чужую задачу,
поправить опечатку в описании, переназначить исполнителя — ежедневные операции.

**Цена.** Возможны случайные правки. Компенсируется историей изменений.

---

<a id="d-12"></a>

## D-12. Удаление задачи — только администратор проекта — **PM**

**Решение.** Участник не может удалять задачи, даже свои. Ненужная задача закрывается.

**Альтернативы.** (а) Разрешить автору удалять свою задачу в течение N минут.
(б) Разрешить всем участникам.

**Почему.** Удаление задачи рвёт ссылки и уносит обсуждение. Ошибочно созданную задачу
дешевле закрыть, чем восстанавливать удалённую.

**Цена.** Мусорные задачи копятся, пока админ не почистит. Открыто на пересмотр, если
пользователь пожалуется.

---

<a id="d-13"></a>

## D-13. Автор задачи — редактируемое поле, создатель — системное — **П + PM**

**Решение.** Требование пользователя «назначить автора задачи» реализуется полем **Автор**,
которое по умолчанию равно создателю, но может быть изменено любым участником. Отдельно
хранится **Создатель** — кто фактически нажал «Создать»; он неизменяем и виден в истории.

**Альтернативы.** Одно поле «Автор», редактируемое (тогда теряется факт, кто создал запись).

**Почему.** Сценарий «завёл задачу с чужих слов» требует смены автора, но система обязана
помнить, кто на самом деле создал объект, — иначе история изменений теряет опору.

**Цена.** Два похожих понятия. В глоссарии зафиксировано жёстко; в UI показывается только
«Автор», «Создатель» виден в первой записи истории.

---

<a id="d-14"></a>

## D-14. Перенос задачи между очередями — не в MVP — **PM**

**Решение.** Задача создаётся в очереди и остаётся в ней. Перенос откладываем в релиз 2.

**Альтернативы.** (а) Перенос со сменой ключа (`DEV-42` → `BUG-7`). (б) Перенос с сохранением
исходного ключа.

**Почему.** Вариант (б) ломает смысл ключа: задача с ключом `DEV-42` лежит в очереди `BUG`,
а номер 42 занят в чужой последовательности. Вариант (а) корректен, но требует таблицы
старых ключей и вечных редиректов — так делает Яндекс Трекер: после переноса задаче
присваивается новый ключ, а ссылки со старым продолжают работать
([документация](https://yandex.ru/support/tracker/ru/user/move-ticket)).

**Цена сейчас.** Ошибочно созданную не в той очереди задачу придётся закрыть и создать заново
вручную (описание и комментарии не переедут). Если это начнёт болеть — поднимаем в релиз 2
в варианте (а). **Подтверждено пользователем (Q12):** в MVP переноса нет, в релизе 2 —
вариант (а) со сменой ключа и постоянным редиректом со старого.

<a id="d-15"></a>

## D-15. Приоритет — число 0–100 с шагом 10, по умолчанию 50 — **П**

**Решение.** 11 значений: 0, 10, …, 100. Больше — важнее. Новая задача создаётся со значением 50.

**Альтернативы для умолчания.** Пустое значение («не задан») или 0.

**Почему.** Пустое значение заставляет каждого заполнять поле вручную; 0 означал бы «совсем
неважно» и искажал сортировку. Середина шкалы — честное «обычная задача».

**Цена.** Голое «70» ни о чём не говорит, поэтому числу нужна словесная опора — границы
диапазонов утверждены отдельно ([D-32](#d-32)). Умолчание 50 подтверждено пользователем.

**Следствие для реализации.** Приоритет **никогда не бывает пустым**: состояния «не задан»
у поля нет, `null` недопустим ни в API, ни в UI.

<a id="d-16"></a>

## D-16. Сложность — story points 1, 2, 3, 5, 8, 13 плюс «не оценено» — **П + PM**

**Решение.** Шкала Фибоначчи задана пользователем. Добавляем пустое значение по умолчанию:
новая задача создаётся без оценки.

**Альтернативы.** Обязательная оценка при создании.

**Почему.** Обязательная оценка при создании тормозит быстрый ввод задач и порождает
случайные цифры.

**Цена.** Часть задач останется без оценки. Приемлемо: агрегатов по сложности в MVP нет.

---

<a id="d-17"></a>

## D-17. Наблюдателей нет, подписка на задачу неявная — **PM**

**Решение.** Уведомления по задаче получают: создатель, автор, исполнитель и все, кто оставил
хотя бы один комментарий. Поля «Наблюдатели» в MVP нет.

**Альтернативы.** Полноценные наблюдатели с кнопкой «Следить».

**Почему.** Неявная подписка покрывает почти все реальные случаи и не требует ни UI, ни
объяснения. Явные наблюдатели без упоминаний `@` дают мало.

**Цена.** Нельзя следить за чужой задачей, не написав в неё комментарий. Нельзя отписаться
от конкретной задачи (только выключить тип события в настройках). Кнопка «Следить» — релиз 2.

<a id="d-18"></a>

## D-18. Уведомления в MVP — только in-app — **П**

**Решение.** Центр уведомлений внутри приложения, счётчик непрочитанных, настройки по типам
событий. Email-канал не делаем, но модель настроек хранит канал как отдельное измерение,
чтобы email добавился без миграции пользовательских настроек.

**Альтернативы.** Сразу email.

**Почему.** Email — это SMTP или внешний сервис, домен с SPF/DKIM, шаблоны, отписка и риск
попасть в спам. Для команды, которая и так весь день в трекере, in-app достаточно.

**Цена.** Пользователь не узнает о назначении задачи, пока не откроет трекер.
**Подтверждено пользователем (Q1):** в MVP только in-app; email — кандидат в релиз 2.

<a id="d-19"></a>

## D-19. Определение «активной задачи» — **П**

**Решение.** Активная задача = я исполнитель И статус не в категории `done`. Ровно это
определение используется в сайдбаре, в поиске по сайдбару и везде, где встречается слово
«активные».

**Альтернативы.** «Все незакрытые задачи проектов, где я участвую» (шумно); «задачи, где
я исполнитель или автор» (сайдбар распухает у того, кто много ставит задач).

**Почему.** Сайдбар отвечает на вопрос «что делаю лично я», а не «что происходит».

**Цена.** Задачи, которые я поставил другим, в сайдбаре не видны — их смотрят в списке очереди.

---

<a id="d-20"></a>

## D-20. Поиск в сайдбаре ищет только по активным задачам — **П**

**Решение.** Строка поиска в сайдбаре фильтрует список активных задач текущего пользователя
по подстроке в названии и по ключу. Глобального поиска в MVP нет.

**Альтернативы.** Сразу глобальный поиск по всем доступным задачам.

**Почему.** Глобальный поиск требует полнотекстового индекса, ранжирования, отдельного экрана
результатов и правил видимости. Это отдельная фича релиза 2.

**Цена.** Чужую или закрытую задачу поиском не найти — только через список очереди.
Риск: пользователь будет считать поиск сломанным. Дизайнеру нужно явно подписать поле
(например, плейсхолдер «Поиск по моим активным задачам»).
**Подтверждено пользователем (Q6):** глобального поиска в MVP нет.

<a id="d-21"></a>

## D-21. Вложения: любой тип, до 25 МБ, превью для изображений — **П + PM**

**Решение.** Ограничение по размеру — 25 МБ на файл (задано пользователем), тип файла
не ограничиваем. Изображения (`image/png`, `image/jpeg`, `image/webp`, `image/gif`)
показываются превью в задаче, остальные — списком с именем, размером и кнопкой скачивания.

**Дополнительно (PM).** Файл вложения доступен только участникам проекта: прямая ссылка
на файл не должна открываться в анонимном браузере. Обложка проекта — отдельное ограничение:
одно изображение, до 5 МБ, только `image/png`, `image/jpeg`, `image/webp`.

**Альтернативы.** Белый список типов файлов.

**Почему.** Белый список бесит команду (архивы, логи, `.drawio`), а безопасность он даёт
мнимую. Ключевое требование — файлы отдаются только участникам и никогда не исполняются
браузером как активный контент.

**Цена.** Диск VPS конечен. **Подтверждено пользователем (Q11):** лимит только на файл
(25 МБ), общей квоты на проект нет; за диском следит инфраструктура. Проверки файлов
на вирусы нет — оговорено явно.

<a id="d-22"></a>

## D-22. Markdown без исполняемого содержимого — **PM**

**Решение.** Описание задачи и комментарии пишутся в Markdown и отображаются отрендеренными.
Поддерживаем: заголовки, жирный/курсив/зачёркнутый, списки (в т.ч. чек-листы), ссылки,
код (строчный и блоками), цитаты, горизонтальную линию, таблицы, изображения по URL.
Не поддерживаем: сырой HTML, скрипты, произвольные схемы ссылок (только `http`, `https`,
`mailto`).

**Альтернативы.** WYSIWYG-редактор.

**Почему.** Markdown — ожидаемый в трекерах формат, дешевле в реализации и переносим.

**Цена.** Часть пользователей не знает Markdown — нужна подсказка по синтаксису в редакторе
(задача дизайнера).

---

<a id="d-23"></a>

## D-23. Один тип задачи; роль типа выполняет очередь — **П**

**Решение.** Поля «Тип задачи» нет. Разделение «фича / баг / дизайн» делается созданием
отдельных очередей — это прямо следует из формулировки пользователя «очередь — пространство
для задач определённого типа».

**Альтернативы.** Поле «Тип» со списком значений.

**Почему.** Тип задачи тянет за собой разные наборы полей и разные воркфлоу — то есть
конструктор, которого в MVP нет.

**Цена.** Смешанную очередь придётся разделять вручную; переноса задач нет (D-14).

<a id="d-24"></a>

## D-24. Удаление очереди — только пустой — **PM**

**Решение.** Очередь можно удалить, только если в ней нет ни одной задачи. Иначе — отказ
с понятным текстом.

**Альтернативы.** Каскадное удаление задач; архивирование очереди.

**Почему.** Каскад — самый лёгкий способ потерять месяц работы одним кликом. Архивирование —
отдельная фича с фильтрами и правами, в MVP не нужна.

**Цена.** Очередь-ошибку с задачами удалить нельзя. Приемлемо для MVP; архивирование —
в релизе 2.

---

<a id="d-25"></a>

## D-25. Удаление проекта необратимо для пользователя — **PM**

**Решение.** Удалять проект может только его администратор, с подтверждением: нужно ввести
название проекта. После удаления проект, его очереди и задачи недоступны никому, ссылки
на задачи отдают 404.

**Альтернативы.** Корзина с восстановлением в UI.

**Почему.** Корзина — отдельный экран, права и правила очистки. Для MVP хватает трения
в виде ввода названия.

**Цена.** Ошибочное удаление восстанавливается только из резервной копии БД руками. Бэкенд
вправе реализовать это как отложенное физическое удаление (это внутреннее решение бэкенда,
на продукт не влияет), но UI восстановления мы не обещаем. Ключи удалённых очередей
**не переиспользуются** — иначе старые ссылки приведут в чужой проект.

---

<a id="d-26"></a>

## D-26. Свежесть данных на экране задачи — **PM**

**Решение.** Изменения задачи и новые комментарии появляются у другого пользователя,
открывшего ту же задачу, без перезагрузки страницы — не позднее чем через 5 секунд.
То же для счётчика непрочитанных уведомлений.

**Альтернативы.** Обновление только по F5.

**Почему.** Двое, обсуждающие задачу одновременно, — базовый сценарий; «нажми F5» выглядит
как поломка. Требование сформулировано по наблюдаемому результату, способ реализации
(WebSocket или опрос) выбирает инженер.

**Цена.** Нагрузка на сервер и дополнительная работа на фронте. В MVP это требование
действует только на экране задачи и на счётчике уведомлений, но не на списках задач.

<a id="d-27"></a>

## D-27. Конфликт одновременного редактирования не решаем — **PM**

**Решение.** Побеждает последняя запись. Блокировок и слияния текстов в MVP нет. Для
описания задачи: если во время редактирования его изменил кто-то другой, при сохранении
показываем предупреждение, что описание изменилось, и даём выбор — перезаписать или отменить.

**Альтернативы.** Совместное редактирование; блокировка на время правки.

**Почему.** Совместное редактирование — отдельный большой проект. Предупреждение снимает
худший случай (молчаливая потеря чужого текста).

**Цена.** Редкие потери правок при гонке. Приемлемо.

---

<a id="d-28"></a>

## D-28. Список задач очереди: сортировка и постраничность — **PM**

**Решение.** Список задач очереди по умолчанию сортируется по убыванию приоритета, при
равенстве — по убыванию номера (сначала новые). Пользователь может переключить сортировку
на «сначала новые». Список подгружается порциями по мере прокрутки, отрисовка виртуализирована.
Фильтр в MVP один — по статусу.

**Альтернативы.** Полноценный конструктор фильтров и сохранённые представления.

**Почему.** Нужно решить, что человек видит, открыв очередь на 500 задач. Фильтры
и сохранённые представления — релиз 2.

**Цена.** Нельзя отфильтровать «задачи Пети с приоритетом выше 70». В MVP приемлемо.

<a id="d-29"></a>

## D-29. Читатель не пишет ничего, включая комментарии — **П**

**Решение.** Роль «читатель» — строго только чтение: ни задач, ни комментариев, ни вложений.

**Альтернативы.** Разрешить читателю комментировать (роль «наблюдатель с правом голоса»).

**Почему.** «Только чтение» — предсказуемая и объяснимая роль. Промежуточный вариант
«читает, но комментирует» требует объяснения в UI и усложняет матрицу прав.

**Цена.** Заказчик, добавленный читателем, не сможет написать «поправьте формулировку» —
ему придётся дать роль участника. **Подтверждено пользователем (Q7).**

**Следствие.** Читатель также не может никого упомянуть (`@`), потому что не создаёт текстов.
Упоминать читателя другие участники могут — он получит уведомление и сможет прочитать задачу.

<a id="d-30"></a>

## D-30. Приглашать в проект может только администратор — **П**

**Решение.** Создание и отзыв ссылок-приглашений — право администратора проекта.

**Альтернативы.** Разрешить участнику приглашать читателей или таких же участников.

**Почему.** Состав проекта = периметр доступа к рабочим данным. Пока команда маленькая,
администратор успевает приглашать сам.

**Цена.** Администратор становится узким местом при быстром росте команды.
**Подтверждено пользователем (Q8).** С введением списка доступа ([D-33](#d-33)) это ещё
и единственный способ впустить нового человека в трекер, поэтому цена выросла: пока админ
не выдал ссылку, человек не войдёт вообще.

<a id="d-31"></a>

## D-31. При исключении участника его задачи остаются, исполнитель очищается — **П**

**Решение.** Исключение из проекта не удаляет ничего: задачи, комментарии и записи истории
сохраняются с указанием авторства. Поле «Исполнитель» в задачах исключённого очищается
системной записью в истории; поле «Автор» сохраняется.

**Альтернативы.** (а) Оставить исполнителя (задача «висит» на человеке без доступа).
(б) Переназначить задачи на администратора автоматически.

**Почему.** Задача с исполнителем без доступа не попадает ни в чей список активных задач
и теряется. Автоматическое переназначение на администратора создаёт ложное впечатление,
что он взял работу.

**Цена.** После исключения кто-то должен вручную разобрать освободившиеся задачи.
**Подтверждено пользователем (Q9).** Исключение из проекта **не** закрывает человеку вход
в трекер: закрыть вход целиком можно только отзывом доступа владельцем трекера
([D-40](#d-40)).

<a id="d-32"></a>

## D-32. Диапазоны приоритета и их названия — **П**

**Решение.** Числовая шкала приоритета делится на четыре диапазона с закреплёнными названиями:

| Диапазон | Значения | Название |
|---|---|---|
| 1 | 0, 10, 20 | Низкий |
| 2 | 30, 40, 50, 60 | Обычный |
| 3 | 70, 80 | Высокий |
| 4 | 90, 100 | Критический |

Значение по умолчанию — 50 (диапазон «Обычный»). Названия диапазонов — часть продуктовой
терминологии: они одинаковы в панели задачи, в фильтрах, в подсказках и в доступных именах
для скринридера. Отдельного поля «диапазон» не существует, он вычисляется из числа.

**Альтернативы.** (а) Только числа, без названий. (б) Заменить число списком из четырёх
значений и убрать шкалу 0–100.

**Почему.** Голое число не читается: «70» ничего не говорит новому участнику. Замена числа
на четыре значения противоречит требованию пользователя о шкале 0–100 с шагом 10.

**Цена.** Два способа говорить об одном и том же («приоритет 80» и «высокий»). Снимается
правилом: в интерфейсе всегда показываем число, название — как пояснение к нему.

<a id="d-33"></a>

## D-33. Вход в трекер — по списку доступа; приглашение пускает в обход списка — **П**

**Решение.** Успешная аутентификация в Яндекс ID сама по себе доступа к трекеру не даёт.
Пользователь попадает внутрь, если выполняется хотя бы одно условие:

1. его email есть в **списке доступа** инстанса;
2. он пришёл по действующей **ссылке-приглашению** — тогда при принятии приглашения его email
   добавляется в список доступа автоматически, с пометкой источника «приглашение».

Список доступа — данные, а не конфигурация. Начальное наполнение приходит из конфигурации
инстанса (нужно, чтобы в пустом трекере было кому создать первый проект), дальше список
живёт своей жизнью и редактируется из интерфейса.

**Альтернативы.** (а) Вход открыт всем владельцам Яндекс-аккаунтов (временное допущение
первой редакции). (б) Ограничение по домену email. (в) Список только в конфигурации,
без экрана.

**Почему.** Инстанс открыт в интернет; без списка доступа любой человек заводит у нас
аккаунт. Вариант (б) не годится: команда работает с личных Яндекс-почт разных доменов.

**Цена.**
- Приглашение становится критичным механизмом: сломается оно — новых людей в трекер не завести.
- Появляется глобальное право, которого в продукте раньше не было ([D-39](#d-39)).

### Дополнение третьей редакции (2026-09-06, ответы на Q14 и Q16)

Пользователь закрыл оба вопроса, вариант (в) отвергнут:

1. **Экран управления списком доступа входит в MVP** ([auth](./stories/auth.md) US-07):
   список записей, добавление адреса, удаление, видимый источник записи и дата. Цена
   отсутствия — вход по SSH на сервер при каждом найме и увольнении, а это хуже, чем один
   простой экран.
2. **Доступ отзывается целиком** ([D-40](#d-40)): удаление записи закрывает вход и гасит
   активные сессии человека.
3. У записи доступа три источника: `config` (пришла из начальной конфигурации инстанса),
   `manual` (добавлена человеком на экране), `invitation` (создана автоматически при принятии
   приглашения). **Внимание:** в `docs/adr/0006-access-list.md` перечислены только `config`
   и `invitation` — значение `manual` появилось вместе с экраном добавления, ADR нужно
   дополнить (зона оркестратора).
4. Ограничение «отозвать доступ нельзя» снято: пункт про это в разделе «Цена» больше
   не действует.

<a id="d-34"></a>

## D-34. Упоминания `@участник` входят в MVP — **П**

**Решение.** В комментариях и в описании задачи можно упомянуть человека через `@`.
Упоминание — это ссылка на пользователя, а не просто текст. Упомянуть можно только участника
проекта, которому принадлежит задача. Упоминание создаёт уведомление и делает упомянутого
подписчиком задачи.

**Альтернативы.** (а) Отложить в релиз 2 (решение первой редакции).
(б) Разрешить упоминать любого пользователя трекера.

**Почему.** Упоминание — самый частый способ позвать человека в обсуждение; без него
обсуждение уезжает в мессенджер и трекер теряет смысл как место обсуждения. Вариант (б)
отпадает: упоминание человека без доступа создаёт уведомление о задаче, которую он не может
открыть, и раскрывает существование проекта.

**Цена.** Нужны пикер в редакторе, подсветка в отрендеренном Markdown, отдельный тип
уведомления и правило «упомянули того, кто потом потерял доступ». Живой сценарий «позвать
человека, которого нет в проекте» не покрыт: пользователь закрыл вопрос Q15 в пользу
приватности состава организации — см. [D-41](#d-41).

<a id="d-35"></a>

## D-35. Адрес проекта — `/projects/<slug>`, старые адреса продолжают работать — **оркестратор + PM**

**Решение.** Проект адресуется человекочитаемым slug, а не идентификатором. Правила:

- slug формируется из названия проекта при создании: транслитерация кириллицы латиницей,
  нижний регистр, пробелы и знаки препинания — в дефис, повторные дефисы схлопываются,
  крайние обрезаются, длина до 40 символов;
- если из названия не получилось ни одного допустимого символа (название из эмодзи
  и знаков) — slug вида `project-<n>`;
- slug **глобально уникален**; при коллизии добавляется числовой суффикс: `sweet-limit-2`;
- **переименование проекта slug не меняет** — иначе разосланные ссылки молча ломаются;
- администратор может изменить slug вручную в настройках проекта;
- при изменении slug **старый адрес продолжает вести на проект** постоянным перенаправлением;
  прежние slug проекта сохраняются, и ни один из них не может быть занят другим проектом.

**Альтернативы.** (а) Адрес по идентификатору (`/projects/7f3a…`) — просто, но нечитаемо.
(б) slug меняется вместе с названием — ломает разосланные ссылки. (в) slug неизменяем
совсем — опечатку не исправить.

**Почему.** Адрес проекта копируют и отправляют людям ([D-04](#d-04)); читаемость важнее
простоты реализации. Механизм «старые адреса ведут на актуальный» — тот же, что понадобится
в релизе 2 для смены ключа задачи при переносе между очередями ([D-14](#d-14)): это
инвестиция, а не разовый костыль.

**Цена.** Нужно хранить прежние slug и делать перенаправление. Slug занимают общее
пространство имён с системными адресами приложения (`/issues`, `/invite`, `/profile`) —
их пересечение нужно исключать при выдаче slug.

<a id="d-36"></a>

## D-36. Один язык интерфейса, но строки вынесены в ресурсы — **П**

**Решение.** Интерфейс только на русском. При этом ни одна видимая пользователю строка
не пишется прямо в виджете: все тексты живут в ресурсах локализации. Добавление второго
языка должно сводиться к переводу файла ресурсов, без правки экранов.

**Альтернативы.** (а) Хардкод строк — быстрее сейчас, дороже потом. (б) Полноценная
локализация с переключателем языка и форматами дат — сейчас не нужна.

**Почему.** Прямое требование пользователя: строки в ресурсах, а не в виджетах.

**Цена.** Небольшой постоянный налог на разработку фронтенда. Переключателя языка,
локализованных форматов дат и множественных форм для других языков в MVP нет.

<a id="d-37"></a>

## D-37. Плоская модель задач: подзадач и иерархии нет даже в модели данных — **П**

**Решение.** Задача не имеет родителя и потомков. Поля «родительская задача» и «подзадачи»
не заводятся ни в API, ни в БД.

**Альтернативы.** Оставить в модели пустое поле «родитель» на будущее.

**Почему.** Пустое поле «на будущее» неизбежно обрастает наполовину рабочей логикой
(отображение, фильтры, каскады) и путает разработку. Когда иерархия действительно
понадобится (релиз 3, вместе с типами задач и эпиками), она проектируется целиком.

**Цена.** Крупную работу приходится дробить на независимые задачи и связывать словами
в описании. При появлении иерархии потребуется миграция данных.

<a id="d-38"></a>

## D-38. Автоссылки на ключи задач и поповер превью — не в MVP — **PM**

**Решение.** Текст `DEV-42` внутри описания или комментария остаётся обычным текстом:
он не превращается автоматически в ссылку и не показывает всплывающее превью задачи.
Ссылку на задачу можно вставить обычной Markdown-ссылкой.

**Альтернативы.** (а) Распознавать ключи и делать их ссылками. (б) То же плюс поповер
с названием и статусом при наведении.

**Почему.** Упоминания `@` уже дают слой разбора текста, и соблазн «заодно сделать и ключи»
велик — но у ключей другая цена: нужно проверять права на каждую упомянутую задачу (иначе
поповер раскроет название задачи из чужого проекта), обрабатывать несуществующие ключи
и держать отдельный запрос на превью. Ценность ниже: адрес задачи и так копируется кнопкой.

**Цена.** Ключи в тексте придётся копировать руками. Автоссылка без поповера — первый
кандидат в релиз 2, она дешёвая. **Важно для дизайна:** в `docs/design/components.md`,
раздел 18, строки «Ссылка на задачу `DEV-42`» и поповер описаны как поддерживаемые —
их нужно перенести в раздел релиза 2, иначе фронтенд возьмёт их в работу как MVP.

<a id="d-39"></a>

## D-39. Право управлять списком доступа — глобальная роль «владелец трекера» — **PM**

**Решение.** Вводится **одна** глобальная роль вне проектной модели ролей: **владелец
трекера**. Только владелец видит и редактирует список доступа.

Правила:

- Признак владельца — свойство пользователя (точнее, его записи в списке доступа),
  а не роль в проекте. С ролями в проектах он никак не связан: владелец трекера может
  не состоять ни в одном проекте, а администратор проекта по умолчанию владельцем не является.
- Записи, пришедшие из начальной конфигурации инстанса (источник `config`), получают признак
  владельца автоматически. Так в свежем инстансе всегда есть хотя бы один владелец.
- Владелец может выдать и снять признак владельца другой записи в списке доступа.
- **Владельцев всегда минимум один:** снять признак у последнего владельца нельзя, удалить
  его запись нельзя.
- **Владелец не может удалить свою собственную запись** и не может снять признак владельца
  с себя, если он единственный владелец. Уходящего владельца удаляет другой владелец.
- Никаких других глобальных прав не появляется: владелец трекера **не получает** доступ
  к чужим проектам, не видит их задачи и не может назначить себя администратором проекта.

**Альтернативы.** (а) Управлять списком может любой администратор любого проекта — отвергнуто:
администратор маленького проекта смог бы впустить в инстанс кого угодно и отозвать доступ
у остальных. (б) Право есть только у записей с источником `config`, менять состав владельцев
можно лишь через конфигурацию и перезапуск — отвергнуто: это ровно та боль, ради которой
делался экран. (в) Полноценный слой глобальных ролей с несколькими уровнями прав
(управление доступом, аудит, обслуживание) — избыточно для команды 3–15 человек.

**Почему.** Право пускать и выгонять людей из инстанса качественно отличается от проектных
прав, и держать его в проектной модели нельзя. При этом заводить целый слой глобальных ролей
ради одного права незачем — достаточно признака «владелец».

**Цена.** В продукте появляется понятие, которого раньше не было («глобальных ролей нет» —
формулировка первой редакции `permissions.md` — больше не верна). Владелец, потерявший
доступ к своему Яндекс-аккаунту, восстанавливается только через конфигурацию инстанса
и перезапуск.

<a id="d-40"></a>

## D-40. Отзыв доступа гасит сессии; данные пользователя остаются — **П**

**Решение.** Удаление записи из списка доступа:

1. закрывает вход: следующая попытка входа через Яндекс ID приводит на экран
   «Доступ к трекеру закрыт»;
2. **немедленно завершает все активные сессии этого пользователя** — во всех вкладках
   и устройствах;
3. **не трогает данные**: комментарии, записи истории, авторство и созданные им задачи
   остаются как есть, с его именем и аватаром;
4. **не трогает членство в проектах**: человек остаётся в списках участников, его назначения
   исполнителем сохраняются. Если доступ вернут, он снова увидит свои проекты.

**Альтернативы.** (а) Отзыв действует только при следующем входе (сессия доживает до
истечения куки) — отвергнуто пользователем: отзыв, который не действует сегодня, бесполезен
в сценарии увольнения. (б) Отзыв заодно исключает человека из всех проектов — отвергнуто:
это разрушает состав команд и необратимо, тогда как отзыв доступа обратим. (в) Обезличивание
данных ушедшего — отвергнуто: история задачи должна оставаться читаемой.

**Почему.** Отзыв доступа — операция безопасности, а не уборка данных. Она должна быть
мгновенной и обратимой, и не должна портить историю.

**Цена.**
- Человек с отозванным доступом остаётся в списке участников проектов и в выборе исполнителя —
  в MVP он никак не помечен (остаточный вопрос Q17).
- Уведомления, адресованные ему, продолжают создаваться, но он их не видит.
- Требование «погасить чужие сессии» — заметное требование к серверу: сессии должны находиться
  по пользователю. Это зафиксировано в `docs/adr/0006-access-list.md`.

<a id="d-41"></a>

## D-41. В подсказке упоминаний — только участники проекта — **П**

**Решение.** Подсказка по `@` показывает исключительно участников проекта, которому
принадлежит задача. Текст `@ivan`, набранный вручную и не выбранный из подсказки, остаётся
обычным текстом: он не подсвечивается, не становится ссылкой и не создаёт уведомления —
независимо от того, существует ли такой пользователь в трекере.

**Альтернативы.** (а) Показывать всех пользователей трекера. (б) Показывать всех и предлагать
пригласить выбранного в проект прямо из комментария.

**Почему.** Подсказка со всеми пользователями раскрывает состав организации любому участнику
любого проекта: достаточно ввести `@а` и посмотреть, кто выпадет. Вариант (б) дополнительно
требует прав на приглашение прямо из редактора, а приглашает у нас только администратор
проекта ([D-30](#d-30)).

**Почему именно так, а не «упомянул — получил ошибку».** Ошибка при вводе `@ivan` тоже
раскрывает информацию («такого нет» против «такой есть, но не в проекте»). Молчаливое
превращение в обычный текст не раскрывает ничего.

**Цена.** Живой сценарий «позовите сюда Петю из соседней команды» не работает: сначала
администратор добавляет Петю в проект, потом его можно упомянуть. Это осознанный ответ
пользователя на вопрос Q15.
