## 1. Что это

**SL Tracker** — веб-трекер задач для небольших команд, ведущих несколько проектов
одновременно. Функциональный ориентир — Яндекс Трекер, но сознательно урезанный: мы берём
из него модель «очередь → задача с человекочитаемым ключом» и отказываемся от всего, что
превращает трекер в конструктор (настраиваемые воркфлоу, свои поля, доски, автоматизации).

Ключевая иерархия: **Проект → Очередь → Задача**.

- **Проект** — рабочее пространство команды: обложка, описание, участники и их роли.
- **Очередь** — пространство внутри проекта для задач одного рода (например, `DEV`, `DESIGN`,
  `BUG`). Очередь даёт задачам ключ и владеет набором статусов.
- **Задача** — единица работы с ключом вида `DEV-42`, описанием в Markdown, вложениями,
  комментариями, историей изменений и полями (статус, приоритет, сложность, автор, исполнитель).

## 2. Для кого

**Основной пользователь** — участник продуктовой команды 3–15 человек (разработчик, дизайнер,
QA, менеджер), которая ведёт несколько параллельных направлений и которой нужен трекер
с нормальными ссылками на задачи и внятной историей, а не таблица в мессенджере.

Три сценария, ради которых продукт существует:

1. **«Что я делаю сейчас».** Открыл трекер — слева список моих активных задач, в нём можно
   быстро найти нужную по названию или ключу.
2. **«Скинь ссылку на задачу».** `https://<домен>/issues/DEV-42` — короткий стабильный адрес,
   который открывается у любого участника проекта и не ломается со временем.
3. **«Что тут вообще произошло».** Открыл задачу — видно описание, обсуждение в комментариях
   с указанием авторов и полную историю изменений полей.

**Не наш пользователь на этом этапе:** крупная организация с матрицей согласований,
служба поддержки с SLA, команда, которой нужны спринты и burndown.

## 3. Чем отличаемся

- **Дёшево заводится.** Вход через Яндекс ID — паролей не заводим и не храним вовсе.
- **Ключ задачи — первоклассная сущность.** Ключ очереди глобально уникален, поэтому ссылка
  на задачу короткая и однозначная, без указания проекта.
- **Меньше настроек — меньше ошибок.** Пять статусов из коробки, один тип задачи,
  фиксированные шкалы приоритета и сложности. Команда начинает работать через минуту после
  создания проекта, а не после часа настройки воркфлоу.
- **Закрытый периметр — на двух уровнях.** В сам трекер попадает только человек из списка
  доступа или пришедший по действующему приглашению; внутри трекера проект виден только
  его участникам. Никаких публичных проектов и никакого «кто угодно по ссылке видит
  содержимое».

## 4. Границы MVP

MVP функционально закрыт: бэкенд (37 путей REST и WebSocket), клиент со всеми экранами,
сквозной набор проверок QA, боевой стенд. Дефекты, найденные сквозным прогоном, ведутся
в [defects.md](../qa/defects.md) — на границы объёма они не влияют.

**Что изменилось в объёме по ходу работы** (чтобы расхождение с первой редакцией не выглядело
случайностью):

- **Тёмная тема добавлена** — раньше числилась в «сознательно не делаем». Оказалась дешёвой,
  потому что дизайн-система построена на ролях цвета, а не на литералах ([D-44](./decisions.md#d-44)).
- **Предупреждение о конфликте редактирования убрано** — раньше требовалось для описания
  задачи. Побеждает последняя запись, молча; цена решения расписана в
  [D-27](./decisions.md#d-27).
- **Список задач очереди в API умеет больше, чем показывает экран:** фильтры по исполнителю,
  автору и границам приоритета поддержаны контрактом, но в интерфейсе MVP есть только фильтр
  по статусу ([D-28](./decisions.md#d-28)). Это задел под релиз 2, а не скрытая функция:
  обещать её пользователю нельзя, пока нет экрана.

### Сознательно НЕ делаем в MVP

| Чего нет | Почему |
|---|---|
| Канбан-доска | Дорого: drag&drop, хранение позиции карточек, реордеринг. Список задач с фильтром по статусу закрывает основную потребность |
| Редактор статусов и воркфлоу | Пяти статусов хватает на старт; модель данных допускает редактор, экран отложен |
| Условия переходов (обязательные поля, ограничения по ролям при переходе) | Требует конструктора правил; в MVP переходы свободные |
| Спринты, планирование итераций, burndown | Мы не Scrum-инструмент; сложность в story points есть, итераций нет |
| Типы задач (баг / эпик / подзадача) | Роль типа выполняет очередь: «очередь — пространство для задач определённого типа» |
| Связи между задачами (блокирует, дублирует, родитель) | **Запрошены пользователем и отклонены им же** ([D-45](./decisions.md#d-45)): без эпиков и подзадач ценность низкая, а цена — обе стороны каждой пары, правила видимости и поведение при удалении. Вопрос закрыт, к обсуждению не возвращаемся |
| Перенос задачи между очередями | Меняет ключ и ломает ссылки; цена описана в [D-14](./decisions.md#d-14) |
| Глобальный поиск и сохранённые фильтры | В MVP поиск — только по активным задачам в сайдбаре |
| Разрешение конфликта одновременного редактирования (блокировки, версии, предупреждения) | Побеждает последняя запись, молча, для всех полей включая описание. Модальное предупреждение отменено пользователем; цена и кандидат в релиз 2 — [D-27](./decisions.md#d-27) |
| Редактирование имени и аватара в трекере | Данные приходят из Яндекс ID; если провайдер не отдал имя, им становится email или логин ([D-43](./decisions.md#d-43)). Редактируемое отображаемое имя — кандидат релиза 2, вопрос Q18 |
| Наблюдатели как отдельное поле | Подписка на задачу неявная: создатель, автор, исполнитель, комментаторы, упомянутые |
| Автоссылки на ключи задач в тексте и поповер с превью задачи | Отдельный слой разбора текста поверх упоминаний; ценность ниже, чем у упоминаний ([D-38](./decisions.md#d-38)) |
| Подзадачи и иерархия задач | Плоский список; в модель данных иерархия не закладывается ([D-37](./decisions.md#d-37)) |
| Сроки (дедлайны), теги, учёт времени | Решение пользователя: не входят |
| Локальный вход по email/паролю | Только Яндекс ID; парольный вход — резервный путь на будущее |
| Мобильное приложение | Запланировано, но не сейчас; API уже проектируется не «под браузер» |
| Публичные проекты, гостевой доступ, экспорт/импорт, интеграции (Git, мессенджеры) | Вне фокуса первого релиза |

### Критерий готовности MVP (проверяемый end-to-end сценарий)

MVP готов, когда команда из трёх человек без участия разработчика может: войти через Яндекс ID
(владелец — из списка доступа) → создать проект → пригласить двоих по ссылке-приглашению,
причём приглашённых нет в списке доступа и они попадают в трекер именно по ссылке →
создать очередь `DEV` → завести 20 задач → назначить исполнителей → провести задачу по всем
пяти статусам → обсудить её в комментариях и позвать коллегу упоминанием `@` → увидеть свои
активные задачи в сайдбаре и найти нужную поиском → получить уведомления о назначении
и об упоминании → посмотреть историю изменений задачи → отправить коллеге адрес проекта
и ссылку на задачу и убедиться, что обе открываются → добавить нового человека прямо
в списке доступа и убедиться, что он входит без приглашения → отозвать доступ уходящему
и убедиться, что его открытая вкладка перестала показывать данные.

**Состояние на 2026-09-10.** Сценарий пройден: пользователь прошёл приложение руками
на боевом стенде, три найденных при этом дефекта исправлены. Дефекты, найденные
автоматическим сквозным прогоном, ведутся отдельно в [defects.md](../qa/defects.md);
их статус — зона QA, на границы MVP они не влияют.

## 5. Продуктовые принципы

1. **Одно понятие — один термин.** Если в глоссарии «задача», то в UI, в API и в разговоре —
   «задача», а не «тикет» и не «issue» (кроме кода и URL, где английский обязателен).
2. **Ключ не врёт.** Ключ задачи публичный и неизменяемый. Любая фича, из-за которой ключ
   меняется, обязана сначала объяснить, что станет со старыми ссылками.
3. **Данные вместо enum.** Всё, что команда захочет настроить завтра (статусы), с первого дня
   лежит в БД как данные, даже если экрана настройки ещё нет.
4. **Ничего не пропадает молча.** Изменение поля задачи оставляет след в истории.
5. **Тишина по умолчанию лучше спама.** Уведомляем только о том, что касается пользователя лично.

## 6. Метрики успеха (оцениваем через месяц после запуска)

- Доля активных задач с заполненным исполнителем ≥ 80 % — иначе трекер не используется по назначению.
- Медиана комментариев на задачу ≥ 1 — обсуждение живёт в трекере, а не в чате.
- Доля задач, дошедших до статуса «Закрыт» за 30 дней, ≥ 60 %.
- Ноль обращений вида «не могу найти свою задачу» (собираем вручную, команда маленькая).

## 8. Открытые вопросы к пользователю

Ни один не блокирует MVP: по каждому есть работающее решение по умолчанию. Ответы нужны,
чтобы планировать релиз 2, а не чтобы запускаться.

| # | Вопрос | Почему важно | Текущее решение (действует, если ответа не будет) |
|---|---|---|---|
| Q17 | Нужно ли помечать в списке участников проекта и в выборе исполнителя человека, **доступ которого в трекер отозван**? | Такой человек остаётся участником проекта и может быть назначен исполнителем, хотя войти уже не может: задача повиснет | Пометки нет. Отзыв доступа не трогает членство ([D-40](./decisions.md#d-40)); чистить состав проекта — ручная работа его администратора. Кандидат релиза 2 |
| Q18 | Разрешаем ли менять **отображаемое имя** в профиле? | Яндекс ID не всегда отдаёт имя и фамилию: у рабочего аккаунта именем стал email, у личного — логин. В списке участников и в выборе исполнителя это плохо читается | Имя приходит от провайдера и в трекере не редактируется. Обходной путь — заполнить имя в аккаунте Яндекса. Варианты с ценой и рекомендация PM — [D-43](./decisions.md#d-43) |
| Q19 | Планируется ли онбординг **больше 20 человек за раз** из одной сети? | Приём приглашений ограничен 20 попытками в минуту на сетевой адрес; за общим NAT 21-й человек получит отказ, а приглашение — единственная дверь в трекер | Ограничение как есть. Для команды 3–15 человек порог не достигается; смена единицы счёта — [D-42](./decisions.md#d-42) |
