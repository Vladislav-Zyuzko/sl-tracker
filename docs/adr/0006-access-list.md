# ADR-0006. Доступ в трекер: список доступа, приглашения, отзыв

- Дата: 2026-09-06
- Статус: принято
- Решает: пользователь; записал оркестратор

## Контекст

Вход в SL Tracker — через Яндекс ID. Инстанс стоит на публичном домене, значит
**войти технически может любой владелец Яндекс-аккаунта**. Аутентификация («это точно
Иван») и авторизация («Ивану сюда можно») — разные вещи, и полагаться на первую вместо
второй нельзя.

Отдельно выяснилось, что членство в проектах не закрывает вопрос: если человека исключить
из всех проектов, войти в трекер он всё равно сможет и увидит пустой экран. Формально
он остаётся внутри периметра.

## Решение

**Два независимых уровня доступа.**

Уровень 0 — доступ в трекер. Уровень 1 — членство в проекте с ролью
(см. `docs/product/permissions.md`).

**1. Вход только по списку доступа.** Пускаем, если email из профиля Яндекс ID есть
в списке доступа (сравнение без учёта регистра) либо человек пришёл по действующему
приглашению. Иначе — сессия **не создаётся** и пользователь в БД **не заводится**.
Экран отказа не раскрывает ни состав трекера, ни его владельца.

**2. Источник правды — таблица в БД.** Переменная окружения
`ACCESS_LIST_BOOTSTRAP_EMAILS` применяется при старте API идемпотентно и нужна только
для начального заполнения: в пустом инстансе иначе некому создать первый проект.
Удаление адреса из переменной не удаляет запись из БД.

**3. Приглашение работает в обход списка** и при принятии добавляет в него запись
с источником `invitation`. Без этого механизм приглашений мёртв: приглашать можно было бы
только тех, кто и так уже имеет доступ.

**4. Доступ отзывается.** Удаление записи из списка доступа закрывает вход, и **активные
сессии этого пользователя гасятся** — иначе отзыв не работает до истечения куки.
Данные пользователя (его комментарии, история, авторство) остаются на месте.

**5. В MVP есть экран управления списком доступа** — добавить адрес, удалить, видеть
источник записи. Без него наём и увольнение сотрудника означают вход по SSH на сервер
и перезапуск сервиса.

**6. Упомянуть можно только участника проекта.** В подсказке `@` показываются исключительно
участники проекта, которому принадлежит задача. Набранный вручную `@ivan` для постороннего
остаётся обычным текстом и не порождает уведомления. Причина: подсказка, показывающая всех
пользователей трекера, раскрыла бы состав организации любому участнику любого проекта.

## Последствия

- Появляется сущность «запись доступа»: email, источник (`config` | `invitation`),
  дата добавления, кем добавлена.
- Отзыв доступа требует умения гасить чужие сессии — сессии должны быть найдены по
  пользователю. Это требование к хранению сессий в Redis (ключ с идентификатором
  пользователя), а не деталь реализации.
- Право управлять списком доступа — новое, глобальное, вне проектной модели ролей.
  Кому оно принадлежит, определяет PM; напрашивается «тому, кто в списке с источником
  `config`», то есть владельцу инстанса.
- Экран управления списком расширяет объём MVP. Это осознанное решение пользователя:
  цена отсутствия — ручное администрирование через SSH.
- Список доступа хранит email — персональные данные. В логи он не пишется.

## Альтернативы

- **Вход открыт всем, изоляция только членством в проектах.** Отвергнуто: посторонние
  заводят учётные записи на нашем VPS, а «уволить» человека нечем.
- **Allowlist по домену email** (пускаем всех с `@company.ru`). Проще в сопровождении,
  но у Яндекс ID массово личные адреса на `@yandex.ru` — правило не сработает.
- **Список только в переменной окружения, без БД и без экрана.** Отвергнуто: каждое
  изменение состава команды требует доступа к серверу и перезапуска.
