# ADR-0002. Весь OAuth идёт через бэкенд, идентичности провайдер-агностичны

- Дата: 2026-09-06
- Статус: принято
- Решает: оркестратор

## Контекст

Вход в SL Tracker — через Яндекс ID по OAuth 2.0. Flutter Web — **публичный клиент**:
всё, что попало в собранное приложение, доступно любому, кто откроет devtools.
`client_secret` в него попасть не может ни при каких условиях.

Второй вопрос — как хранить связь «наш пользователь ↔ аккаунт у провайдера». Соблазн —
положить `yandex_id` полем в таблицу `users`. Это работает ровно до того дня, когда
понадобится второй способ входа.

## Решение

**1. Обмен кода на токен происходит только на сервере.**

```
Flutter → GET /api/auth/yandex/start
            бэкенд генерит state (≥32 байта), кладёт в Redis с TTL, редиректит
         → oauth.yandex.ru/authorize
         → GET /api/auth/yandex/callback?code&state
            бэкенд проверяет state, меняет code на токен (client_secret здесь),
            тянет login.yandex.ru/info, делает upsert users + identities,
            ставит httpOnly cookie, редиректит в приложение
Flutter → GET /api/me
```

Фронт не видит яндексовых токенов вообще. Он знает только про свою сессию.

**2. Идентичности вынесены в отдельную таблицу.**

`identities(provider, external_id, user_id)` с уникальным составным индексом.
В `users` нет ни одного поля, называющего провайдера.

**3. Сессионный слой поддерживает две стратегии с первого дня:** cookie (веб)
и `Authorization: Bearer` (будущий мобильный клиент, PKCE + app links).
Доменный код не знает, какая из них использована.

## Последствия

- Добавить второй провайдер или локальный вход по паролю — это новая строка в `identities`
  и новый контроллер, без миграции пользователей.
- Мобильный клиент не потребует переделки авторизации на сервере.
- `state` обязателен и обязателен к проверке — без него callback принимает чужой `code` (CSRF).
- Яндексовый access-токен после получения профиля не хранится. Если он когда-нибудь
  понадобится для интеграций — только в зашифрованном виде и отдельным решением.
- **Email из профиля Яндекса не является доверенным идентификатором.** Склейка аккаунтов
  по совпадению email запрещена: это классический путь захвата чужого аккаунта.
  Совпал email — заводим отдельного пользователя, склейка только по явному подтверждению.

## Альтернативы

- **PKCE прямо во Flutter Web, без участия бэкенда.** Формально возможно, но тогда токены
  провайдера оказываются в браузере и их надо где-то держать. Отвергнуто.
- **Готовый identity-провайдер (Keycloak, Authentik) как брокер.** Даёт много из коробки,
  но это ещё один сервис на VPS, своя база, свои обновления и своя модель данных.
  Для одного разработчика и одного провайдера входа — избыточно.
